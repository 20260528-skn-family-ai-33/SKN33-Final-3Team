# Report Agent 오프라인 평가

평가일: 2026-11-09 (KST) · 관련 이슈 #82

## 목적과 평가 범위

채팅 에이전트의 Report Agent가 설계(`docs/AGENT_DESIGN.md` D-76·D-81·D-90·D-92·D-93·D-96·D-97, §14.6)대로
리포트 요청을 승인받고, 접수하고, 완성까지 기다렸다가 답하는지 실제 실행으로 평가한다.
또 승인한 분석 결과로 만든 리포트 파일이 결과표를 그대로 싣는지 확인한다. 작업 전·후에 같은 입력·기대 결과·판정 기준을 쓴다.

**이 문서의 점수는 선정한 설계 계약 사례의 통과율이다. 실제 사용자 질문의 분포나 서비스 전체 정확도가 아니다.**
LLM 플래너·답변 초안은 Mock으로 고정했고, 리포트 파일 생성은 완료 신호(`report.status`)로 대신한 사례가 있다.

Report Agent 코드: `backend/app/agents/report.py`(미리보기·접수·대기 깨우기), `agents/conditions.py`(수입 거부·미리보기 호출),
`agents/clarification.py`(승인 버튼 검증), `agents/graph.py`(리포트 대기 중단점), `agents/runtime.py`(`report_ready`).

### 해석

- **채팅 흐름(승인·대기·완료·선행 결과) 18개는 작업 전부터 모두 통과했다.** 이번 작업에서 처음으로 이 계약들을 사례로 고정했고,
  기존 구현이 설계대로 동작함을 확인했다. 앞으로 다른 변경이 이 흐름을 깨면 평가가 실패한다.
- 개선은 리포트 파일이다. 작업 전에는 승인한 결과로 만든 리포트가 요청형 HTML 템플릿을 쓰지 않고 기본 양식(ReportLab)으로 만들어졌고(R19),
  일회성 판정이 `{'suspected': False, ...}` 같은 원시 값으로 찍혔다(R21). 결과표 분량 제한·누락 안내 기능이 없었다(R22).
- R20(조건으로 요청한 리포트는 기존 템플릿 유지)은 작업 전에도 통과한다. 개선이 기존 요청형 리포트를 바꾸지 않았음을 확인하는 사례다.

## 사례와 판정 기준

| 사례 | 분류 | 기준 |
|---|---|---|
| R01 | 명시 승인 | 미리보기를 만들어 묻고, 입력창의 글은 승인으로 쓰지 않으며 리포트를 만들지 않는다(D-81·D-92). 짧은 승인 말은 버튼 안내, 그 밖의 글은 조건 수정으로 다시 묻는다(§13.6). |
| R02 | 입력 검증 | 다른 미리보기·지원하지 않는 형식·중복·빈 형식·문자열 확인값은 4xx로 거부하고 아무것도 접수하지 않는다. |
| R03 | 형식 보존 | 사용자가 고른 PDF·DOCX(한 개 이상, 중복 없음)를 리포트에 남긴다. |
| R04 | 지원 범위 | 수입 리포트는 미리보기·리포트 없이 안내하고 수출로 바꾸지 않는다(D-81). |
| R05 | 취소 | 취소하면 리포트를 접수하지 않는다. |
| R06 | 만료 | 승인 뒤 실행 전에 미리보기가 만료되면 새 미리보기로 다시 묻는다. |
| R07 | 완료 대기 | QUEUED·RUNNING·DELAYED 동안 대기하고 READY에서 리포트 번호와 완료 문구로 끝난다(D-76·D-93). |
| R08 | 실패 처리 | 리포트 FAILED면 완료 문구 없이 그 질문만 NO_DATA, 같은 질문의 통계 분석은 답한다(D-72). |
| R09 | 중복 방지 | 같은 job·단계를 다시 실행하면 리포트를 재사용하고 승인 입력이 다르면 접수하지 않는다(D-97). |
| R10 | 대기 확인 | 한 번에 1건씩만 확인해도 커서로 이어 보며 대기 채팅 3개를 모두 깨운다(§14.6). |
| R11 | 완료 제목 | 첫 답변의 제목은 20자 이내, LLM을 다시 부르지 않는다(D-93). |
| R12 | 조건 충돌 | 조건이 다른 두 선행 결과를 합치지 않고 리포트만 NO_DATA로 끝낸다(D-90). |
| R13 | 조건 고정 | 선행 결과 기반 리포트는 글로 조건을 바꾸지 않고 새 분석을 안내한다(D-92). |
| R14 | 그래프 중단 | 리포트 대기 중 그래프가 실행권을 놓고 완료 후 이어서 재개한다(기존 테스트). |
| R15 | 실행 예산 | 실행 예산을 다 써도 완성된 리포트의 결과 확인을 거부하지 않는다(기존 테스트). |
| R16 | 부분 결과 | 선행 결과의 누락(PARTIAL)을 리포트 결과까지 전파한다(D-96, 기존 테스트). |
| R17 | 완료 결론 | 요약 정보가 없어도 리포트 성공 결론을 고정 문구로 만든다(D-93, 기존 테스트). |
| R18 | 결과 고정 | 원본 결과가 만료돼도 승인한 사본으로 재조회 없이 문서를 만든다(D-90, 기존 테스트). |
| R19 | 템플릿 | 결과 기반 리포트도 요청형 템플릿으로 결과표·그래프를 싣고, 결과표에 없는 섹션은 알리며, 통계를 다시 조회하지 않는다. |
| R20 | 기존 유지 | 조건으로 요청한 채팅 리포트는 기존 요청형 집계 섹션을 그대로 쓴다. |
| R21 | 표시 | 일회성 판정·순위 상태를 PDF·DOCX에서 읽을 수 있는 말(판정 전·해당 없음 등)로 싣는다. |
| R22 | 분량·누락 | PDF 결과표는 200행까지 싣고 전체 행 수·누락 사유·미포함 항목을 알리며, 시리즈 5개 초과 추이는 표만 둔다. |

R01–R13·R19–R22는 `backend/tests/test_agent_report.py`, R14–R18은 기존 테스트를 재사용한다.
R01–R13·R19–R21은 채팅 API → 워커(`run_once`) → LangGraph → 리포트 접수·생성까지 실제 코드를 SQLite에서 끝까지 실행한다.

### 채점

- unittest 테스트 메서드 하나가 사례 하나다. subTest가 하나라도 실패하면 그 사례는 FAIL이다.
- 예외는 ERROR, 건너뜀은 SKIP으로 기록하며 모두 분모에 포함한다. 통과율 = PASS 수 / 등록 사례 수 × 100.
- 평가 중 외부 네트워크 연결은 막는다(Windows asyncio가 쓰는 127.0.0.1 연결만 허용).

## 재현 방법

저장소 루트에서 백엔드 의존성이 설치된 Python 3.11 이상 환경을 쓴다. LLM·RDS·Redis·Chroma·API 키는 필요 없다.

```powershell
python -m backend.scripts.evaluate_report_agent --output docs/evaluations/report_agent_current.json
python -m backend.scripts.evaluate_report_agent --source-ref c6e6bcd --output docs/evaluations/report_agent_before.json
python -m unittest backend.tests.test_agent_report
```

현재 평가는 종료 코드 0, 작업 전 비교는 미통과 사례가 있어 종료 코드 1이 정상이다.

웹 열람 화면은 브라우저 테스트로 따로 확인한다(통과율에 넣지 않음). 결과 기반 리포트에서 '포함되지 않음' 안내 2곳, '—억 USD'·'준비 중' 미표시,
결과표 값, 국가별 추이 선 2개, 원본 결과 API 미호출을 확인한다.

```powershell
cd frontend; node tests/report-view-browser.cjs
```

## 미평가 및 후속 항목

- 실제 LLM의 리포트 의도 판단·조건 해석 정확도: 플래너를 Mock으로 고정해 측정하지 않았다.
- 운영 MySQL·다중 워커 경합·프로세스 강제 종료 중 리포트 대기 복구: 별도 통합 검증이 필요하다(설계 §2026-11-03 구현 현황).
- 리포트 대기의 전체 시간 상한(C-24): 현행대로 별도 상한 없이 리포트 자체 재시도·실패 정책을 따른다.
- 채팅 결과 기반 리포트에 채팅에서 찾은 기사 근거를 싣는 것은 D-90(기사 원문은 사본에 넣지 않음)과 맞춰 팀 확인 후 진행한다.
- 웹 결과 화면은 일회성 판정 칸을 "—"로 표시한다(`frontend/src/api/hooks.jsx`). 리포트 파일과 같은 문구로 맞출지는 별도 작업이다.
