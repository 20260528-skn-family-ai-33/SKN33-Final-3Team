# SQL·Visualization 질문 Holdout 평가

평가일: 2026-11-09 · PR #75 / 이슈 #74

**새 질문 30개를 고정한 후 `e465dd962deafa5aecd4354eb937d4cbc5a02776`의 코드·프롬프트로 한 번만 실행했다.**
정상 조회 결과 일치율은 **18/20(90%)**이며, 실패를 보고 수정하거나 재실행하지 않았다.
결과 원본은 [sql_holdout_result.json](evaluations/sql_holdout_result.json)이다.

정답 SQL·질문은 AI가 작성하고 SQL 결과를 별도 Python 계산과 대조했으며 **사람 검토는 대기 중**이다.
기존 합성 DB를 재사용하는 **질문 holdout**이다. 새로운 실제 데이터나 독립 전문가가 만든 검증 세트의 성능은 아니다.

## 실행 격리와 고정 조건

- 원래 작업 폴더의 `fix/83-FunctionFix`는 유지했다. 기존 변경 파일을 stash/reset/checkout하지 않았다.
- 별도 worktree `tmp/holdout-74`에 `feat/74-SqlVisualization`을 열어 평가 자료만 추가했다.
- `backend/app/` 전체, 기존 `evaluate_sql_live.py`와 `evaluate_sql_visualization.py`, 기존 질문·정답·스냅샷은 기준 커밋 그대로다.
- 새 실행기는 기존 평가기의 질문·manifest 경로와 보고서 메타데이터만 연결한다.
  생성·검증·SQL 실행·재생성·차트·채점 함수와 임계값을 변경하지 않았다.
- 실행 전후 Git diff와 SHA256을 확인했다. 코드·프롬프트·질문·DB 행 해시는 실행 중 바뀌지 않았다.
- [실행 잠금 기록](evaluations/sql_holdout_run_lock.json)이 있으면 재실행을 거부한다.
  운영 정책의 문항 내 재생성은 그대로 적용하며, 평가 전체는 한 번만 실행했다.
- 로컬 MySQL `8.4.11`, `synthetic-trade-v1`, 기준월 `2025-03`, SELECT 전용 계정으로 평가했다. 아래 결과는 평가 당시 모델 `gpt-4.1-2025-04-14`로 측정했다.
  운영 RDS는 사용하지 않았다. 20초 LLM 시간 제한, 최대 2회 재생성, 기존 숫자 오차 기준을 유지했다.

## 새 질문 구성

[질문·정답](evaluations/sql_holdout_questions.jsonl), [고정 시각·해시](evaluations/sql_holdout_manifest.json),
[사람 검토용 SQL·결과표](evaluations/sql_holdout_gold_review.md)를 함께 보존했다.

기존 40문항과 동일 질문·정답 SQL은 없으며, 각 문항의 `novelty`에 새로운 평가 관점을 기록했다.
숫자나 국가만 바꾼 복제에 머무르지 않도록 데이터 품질 건수, 가중 단가 순위, HAVING,
복수 국가 묶음, 무역수지, 길이가 다른 기간, 직전 월 비교, 상대 위치 비교 등을 넣었다.
6개 유형별 5문항으로 요청한 유형별 4개 이상을 충족한다.

| 유형 | 문항 | 결과 정답/올바른 거부 |
|---|---|---:|
| 물량·단가 | H01–H05 | 4/5 |
| 여러 품목 합산 순위 | H06–H10 | 5/5 |
| 국가 묶음 합계·집계 | H11–H15 | 4/5 |
| 기간 비교 | H16–H20 | 5/5 |
| 미지원·금지 요청 | H21–H25 | 5/5 |
| 모호한 질문 | H26–H30 | 5/5 |

전체 국가 또는 전체 품목을 정상적으로 요청하는 문항은 **13개**다.
H01·H02·H12·H14·H16은 국가와 품목 모두 전체다.
전체 범위 13개 모두 SQL 실행에 성공했고, **명시적 과잉 거부는 0건**, 결과 정답은 **12/13**이었다.
오답 H15도 실행·단가 계산은 완료됐으며 열 구성 때문에 실패했다.

## 실패 2건과 해석

- **H05 — 건수 단위 누락:** 값은 정답과 같은 `1건, 674kg`이지만 건수 열의 `unit`이
  `COUNT` 대신 null이었다. 기존의 단위 포함 채점 규칙을 그대로 적용해 오답 처리했다.
- **H15 — 요청하지 않은 열 추가:** 요청한 HS6 코드·가중 단가 외에 금액 합계·중량 합계 열을 추가했다.
  단가 수치는 정답과 같지만 열 구성과 단위 목록이 달라 오답이었다. 서로 다른 단위의 숫자 열이
  섞여 기존 Visualization이 차트를 생략했고, 기대한 bar와도 불일치했다.

두 건을 잘못된 금액·중량 계산으로 해석하지 않는다. 단위와 결과 형식을 포함하는 기존 점수는 그대로 **90%**다.
지금 이 실패를 고치면 이 질문 세트는 이후 개선 코드에 대해 development로 구분해야 한다.
이번 작업에서는 해당 문제를 수정하지 않았다.

## 검증과 실행 기록

- 정상 조회 정답 SQL 20개를 실제 로컬 MySQL에서 실행하고, 별도의 Python 행 집계와 모두 대조한 뒤 고정했다.
- 새 실행기의 단일 실행 차단·점수 보존·질문 구성 검사 3개가 오프라인으로 통과했다.
- 저장된 응답으로 기존 `score_case`·`summarize_live`를 다시 계산해 원본 점수와 일치하는지 확인했다.
  이 검증은 모델/DB를 재호출하지 않는다.
- [텍스트 실행 로그](evaluations/sql_holdout_execution.log), 원본 JSON, 실행 잠금 파일을 함께 보존했다.
- 평가 후 전용 MySQL 컨테이너를 중지했다. 기존 작업 브랜치는 전환하지 않았다.

실행했던 명령(이미 완료했으므로 같은 holdout은 재실행하지 않는다):

```powershell
python -m backend.scripts.prepare_sql_holdout
python -m unittest backend.tests.test_sql_holdout_evaluation
python -m backend.scripts.evaluate_sql_holdout --run-live --env-file <기존_작업폴더>/.env --max-cost-usd 1
```

추가 검토 시 주의할 점:

- 소규모 단일 실행이며 확률적 출력의 분산이나 통계적 신뢰구간을 추정한 실험은 아니다.
- 확정 조건을 SQL 노드에 제공했다. Planner의 조건 추출·되묻기 전체 흐름은 평가하지 않았다.
- 시각화는 저장 결과 어댑터를 통한 ChartSpec의 유형/생략 검사이며 브라우저 렌더링 검증이 아니다.
- 같은 스키마·합성 데이터·유형을 사용하므로 서비스 전체의 일반 정확도로 확대 해석할 수 없다.
- 정답 검토표의 사람 검토를 완료해야 공식 정답 세트로 확정할 수 있다.
