# 컨텍스트 관리 테스트 계획서 (이슈 86)

## 1. 목적
여러 턴 대화에서 이전 조건을 맞게 이어받고, 바뀐 조건만 갈아끼우고, 초기화 요청은 해제하는지 측정한다. 대상은 플래너의 생략(null) 처리, 조건분석의 이어받기(D-22), 컨텍스트 저장(`completed_context`·`SessionContext.remember`)이 함께 만드는 결과다.

## 2. 범위
| 포함 | 제외 |
|---|---|
| `planner_input`의 previous_conditions·recent 전달 | Redis 저장·복구(`ChatContext.load/publish`). 단위 테스트(`test_agent_context.py`)가 맡는다 |
| 플래너의 후속 질문 슬롯(생략·초기화·전환) | 오래된 캐시 판정(last_job_id), 조건 초기화 API(API-39) |
| 조건분석의 이어받기·새 국가 처리 | 답변 요약(turn_summary) 생성 품질. compose와 떼려고 정답 요약을 쓴다 |
| `completed_context`: 성공 턴만 저장, 대화형 턴은 조건 유지, 최근 5턴 | 되묻기 답 이후 재개 |

## 3. 평가 모델
planner 계획서와 같다. 기준선 `gpt-4.1-mini`, 후보 `gpt-5.6-luna`·`gpt-6-luna`.

## 4. 환경·전제
- LLM(`OPENAI_API_KEY`)과 RDS(조회만, 턴마다 rollback)를 모두 쓴다.
- 품목은 숫자 HS 코드로 쓴다. 품목명 검색 결과가 섞이지 않게 하려는 것이다.
- 각 턴의 답변 요약은 시나리오에 적은 정답 요약을 쓴다. 다음 턴의 recent에 들어간다.
- 컨텍스트에는 하위 질문이 하나이고 조건 확인이 DONE인 턴, 또는 대화형(CONVERSATION) 턴만 남긴다. 실제 흐름처럼 되묻기에 걸리거나 실패한 턴은 남기지 않는다.
- 첫 턴은 첫 질문(`first_question`)으로 실행한다. 관심 범위는 비워 두어 관심 범위 되묻기는 나오지 않는다.
- 2024·2025년 기간 데이터가 RDS에 있어야 한다.

## 5. 테스트셋
**파일**: `backend/evals/agent/cases/context.jsonl` (20개 시나리오, 48턴: dev 10개·24턴 / holdout 10개·24턴)

### 5.1 문항 형식
```json
{"id":"s001","split":"dev","tags":[...],
 "turns":[{"question":"...","summary":"정답 요약",
           "expect":{"intent":"STATISTICS","status":"DONE",
                     "conditions":{"country_codes":["VN"],"hs_codes":["330499"],"period":{...},
                                   "trade_flow":"EXPORT","compare_period":null}}}]}
```
- `expect.intent`: 기대 intent. 둘 다 맞으면 `{"$in":[...]}`
- `expect.status`: 첫 하위 질문의 조건 확인 상태. 분석 턴은 `DONE`, 대화형 턴은 조건 확인 단계가 없어 `NO_STEP`
- `expect.conditions`: 첫 하위 질문의 확정 조건. 칸 규칙은 조건분석 계획서와 같다(`country_codes`·`hs_codes`·`period`·`period_months`·`compare_period`·`trade_flow`·`article_period`·`ranking_group`·`ranking_limit`).
- 모든 턴은 하위 질문이 하나여야 한다(`task_count`).

### 5.2 유형 분포
| 유형 | 태그 | dev | holdout |
|---|---|---|---|
| 이어받기 | inherit | 2 | 2 |
| 국가 전환·되돌리기 | country_switch·back_and_forth | 2 | 2 |
| 품목 전환 | product_switch | 1 | 2 |
| 초기화(국가·품목) | reset·product_reset | 2 | 2 |
| 중간 대화형 질문 | conversation_between·term_first | 2 | 2 |
| 기간·비교 변경 | period_switch·recent_months·compare_followup | 3 | 3 |
| intent 전환 | intent_switch·news·ranking_followup | 2 | 2 |
| 수입 방향 유지 | trade_flow | 1 | 2 |

숫자는 그 유형 태그가 하나라도 붙은 시나리오 수다(한 시나리오이 여러 유형에 걸칠 수 있다). holdout은 유형마다 2시나리오 이상이다.

## 6. 실행 방법
```bash
.venv/Scripts/python.exe -m backend.evals.agent.run context --split dev --model gpt-4.1-mini,gpt-5.6-luna,gpt-6-luna
# 추론 모델의 일관성을 보려면 --repeat 3 (비용 3배)
# 개선 완료 뒤 1회
.venv/Scripts/python.exe -m backend.evals.agent.run context --split holdout --model gpt-4.1-mini,gpt-5.6-luna,gpt-6-luna
```
세 모델을 한 명령으로 차례로 돌리고, 결과를 한 쌍의 파일로 남긴다: `output/agent_eval/context_<split>_compare_<시각>.md`(모델별 지표·문항별 통과 비교 표)와 같은 이름의 `.json`(모델별 요약과 문항별 전체 결과). `.json`의 `score.turns[]`에 턴별 intent·확정 조건·판정이 남는다.

## 7. 평가 지표
| 지표 | 정의 | 계산 | 목표(제안) |
|---|---|---|---|
| **턴 통과율** (주 지표) | intent·상태·하위 질문 수·기대 조건·컨텍스트 저장이 모두 맞은 턴 비율 | `turn_pass_rate` | ≥ 90% |
| 컨텍스트 저장 정확도 | 저장한 턴에서 확인: 최근 대화 끝에 이번 질문·intent·정답 요약·확정 조건이 붙음, 앞 대화는 최근 4개 유지, 최근 조건이 이번 조건(대화형 턴이면 이전 조건) | 턴별 `fields.context_saved` | 100% |
| 시나리오 통과율 | 모든 턴이 통과한 시나리오 비율 | 통과 시나리오 / 전체 | ≥ 80% |
| 유형별 통과율 | 태그별 시나리오 통과율 | `summary.by_tag` | 각 유형 실패를 원인별로 기록 |
| 턴 지연 p50·p95·최대 | 턴 1개(플래너 + 조건 확인) 소요(ms) | `turn_latency_ms_*` | p95 ≤ 25,000ms (플래너 10초 + check 15초) |
| 시나리오 지연 p50·p95 | 시나리오 1개 전체 소요(ms) | `latency_ms_*` | 참고값 |
| 총 소요 | 평가 전체 실행 시간(초) | `elapsed_seconds` | 참고값 |

**실패 원인 분류** (턴 결과를 보고 수동으로 적는다)
| 분류 | 예 | 고칠 곳 |
|---|---|---|
| 플래너 생략 실패 | "미국은?"에 이전 품목을 다시 적지 않고 다른 품목을 지어냄 | 플래너 프롬프트 |
| 초기화 실패 | "한국 전체"인데 countries=null(이어받기) | 플래너 프롬프트 |
| 이어받기 판정 오류 | 다시 적은 이전 조건이 거부됨, 새 국가가 있는데 이전 국가가 남음 | conditions D-22 |
| 컨텍스트 저장 오류 | 대화형 턴 뒤 조건이 사라짐, 실패 턴의 조건이 남음 | context `completed_context` |
| 정답 오류 | RDS에 없는 기간·코드 | 테스트셋 |

## 8. 판정 규칙
1. 플래너 모델 선택은 planner 계획서의 holdout 결과를 주로 보고, 이 평가는 보조 지표로 쓴다. 턴 통과율이 90% 아래인 모델은 뺀다.
2. 같은 실패가 여러 모델에서 나오면 모델 문제가 아니라 프롬프트·코드 문제로 보고 고친다.
3. 표본 1턴이 dev·holdout 모두 약 4%p다. 그보다 작은 차이는 같은 수준으로 본다.

## 9. 위험·주의
- 앞 턴이 실패하면 뒤 턴 맥락이 달라져 실패가 이어질 수 있다. 판정은 턴별로 하되, 원인은 첫 실패 턴에서 찾는다.
- 시나리오가 최대 3턴이라 최근 5턴을 넘기는 경우(오래된 턴 버리기)는 실제로 일어나지 않는다. `context_saved` 검사는 그 규칙도 보지만, 확인은 단위 테스트가 맡는다.
- 정답 요약을 쓰므로 실제 compose 요약 품질이 맥락에 주는 영향은 측정하지 않는다.

## 10. 결과 기록 양식
비율 칸은 %로 적는다. 결과 JSON의 비율은 0~1이다(1 = 100%). ↓ 표시는 낮을수록 좋은 지표이고, 나머지는 높을수록 좋다. 시간은 결과 JSON의 `latency_ms_*`(실행 1회)와 `elapsed_seconds`(평가 전체)를 옮긴다.

|---|---|---|---|---|---|---|---|---|---|---|---|
