## 2026-11-09 알파테스트 후속 엑셀 양식 점검

프론트 다운로드 버튼, API-42·48·134, XLSX 생성기 호출 경로를 점검했다. 에이전트 결과표와 요청형 리포트의 엑셀은 수정 범위에서 제외한다.

| 다운로드 경로/양식 | 유지 컬럼 및 변경 |
| --- | --- |
| 수출입 순위 → 교역국 순위(API-20 → 42) | 순위, 국가명, 수출액(USD), 수입액(USD), 선택한 수출/수입 기준 비중(%). 국가 코드는 국가명으로 표시하고 순위 변화·순위 상태·전월 대비·전년 대비·일회성 판정 제외 |
| 수출입 순위 → 품목 순위(API-20 → 42) | 순위, HS 코드, 품목명, 수출액(USD), 수입액(USD), 선택 기준 비중(%). 위 분석 컬럼과 비어 있는 국가 코드 열 제외, HS 코드와 품목명 머리글 구분 |

수출입 API의 `items`와 계산값은 유지한다. 화면 전용 `screen_export=True`일 때 저장 결과의 표시 컬럼을 지정하므로 같은 함수를 기본 옵션으로 호출하는 채팅·에이전트에 영향을 주지 않는다. 국가명은 다운로드 결과를 저장할 때 국가 마스터에서 일괄 조회한다. 화면용 품목 스냅샷은 별도 문자열 `hs_code`를 표시하여 빈 결과에서도 HS 코드 머리글이 유지된다. 원본 USD 숫자, 비중 값, 실적 없는 행의 빈 셀 및 상위 1,000행 제한·안내는 유지한다.

정기 리포트 정비는 XLSX 생성 시에만 적용하고 웹/PDF/DOCX의 원본 표를 변경하지 않는다. 비교표 저장과 전체 XLSX 생성은 `PERIODIC_REPORT_TYPES`의 주간·월간·분기를 공통으로 정기 리포트로 판단한다. 요청형 리포트와 `freshness=FROZEN` 문서는 기존 양식을 보존한다. `build_document`가 `source_tables`를 재사용할 때 항상 `FROZEN`을 기록하므로 XLSX 생성에서는 이 표시만 검사하며, 생성 후 `source_tables`가 빠져도 원본 양식을 보존한다. 기존에 저장된 결과 스냅샷·리포트 파일은 덮어쓰지 않는다. 새 수출입 조회와 새 정기 리포트 생성부터 적용되며, 파일이 없는 정기 리포트의 다운로드 시 생성 경로에도 적용한다.

재검수에서 일반 다운로드의 정보 시트도 정비했다. 수출입 화면용 스냅샷은 `export_profile=TRADE_SCREEN`, 정기 리포트의 한국 전체/상대국 비교 스냅샷은 `PERIODIC_REPORT`로 출처를 표시한다. API-42는 이 두 출처에만 일반 정보 양식을 적용한다. 정기 리포트 전체 파일도 같은 양식을 쓴다. 실행 SQL, 내부 버전·상태·원시 JSON 항목을 제외하고 조회/비교 기간, 품목·국가 코드, 조회/비교 기준, USD 단위, 출처, 최신 공개 월, KST 생성 시각, 전체 행 수를 읽을 수 있는 제목으로 표시한다. 주의사항, 월평균 비교 근거, 상위 1,000행 안내 및 한국 전체/상대국의 중복 합산 주의는 유지한다. 표시가 없는 에이전트·과거 결과는 기존 정보 시트를 유지한다.

리뷰 후 국가 조건 설명을 집계 범위와 맞췄다. 한국 전체 포함 리포트는 정보 시트에 `조회 국가: 한국 전체 (비교 상대국: US, CN)`을 표시하며, 상대국이 없으면 `한국 전체`로 표시한다. 개별 비교표 스냅샷에서는 리포트 전용 `include_korea_total` 조건이 제외되므로 보존된 `overlapping_scopes` 표시를 사용한다. 한국 전체 미포함일 때는 기존 국가 코드/전체 국가 표시를 유지한다. 표의 집계값과 조건 원본은 바꾸지 않는다.

## 2026-11-09 기능 테스트 합의 반영

- 이메일 계정은 앞뒤 공백만 제거하고 **주소 전체의 대소문자를 구분**한다. 가입·중복 확인·로그인·등록 이메일 확인·비밀번호 변경·가입 여부 확인·임시 비밀번호 발급에 같은 기준을 적용한다. 요청 제한은 같은 메일함에 대한 남용을 막기 위해 기존처럼 대소문자를 묶는다. 아래 과거 기록의 소문자 정규화 정책보다 이 결정이 우선한다.
- 기존 이메일·비밀번호·세션 데이터는 변환하지 않는다. 과거 소문자로 저장한 계정은 저장된 소문자 주소로 로그인한다. 신규 주소는 입력 대소문자를 보존한다.
- 운영 DB의 `users.email`은 2026-11-09 읽기 전용 확인 당시 `utf8mb4_0900_ai_ci`였다. **대소문자만 다른 주소를 별도 가입하려면 배포 전에 마이그레이션이 필요하다.** `python -m backend.scripts.migrate_email_case`는 계획만 출력하고, `--apply`를 붙이면 해당 컬럼의 비교 규칙을 `utf8mb4_bin`으로 바꾼다. 기존 UNIQUE 인덱스·주소를 보존하고 컬럼 주석은 초기 스키마와 일치시킨다. 비교 규칙과 주석 모두 반영되면 재실행 시 생략한다. 이번 작업에서 운영 DDL은 실행하지 않았다.
- 마이그레이션 전후 모두 계정 조회는 `email = :email`로 UNIQUE 인덱스를 사용한 뒤 Python에서 대소문자를 정확히 비교한다. 사용자 행 잠금도 같은 인덱스 조회를 사용한다. 가입 중 이메일 UNIQUE 충돌은 재시도 대상이 아닌 `409 EMAIL_ALREADY_EXISTS`로 응답한다. 운영 RDS 읽기 전용 `EXPLAIN`에서 종전 `COLLATE` 조건의 `ALL` 스캔이 수정 후 `const`·`uq_users_email`·1행 조회로 바뀐 것을 확인했다. 관리자 회원·감사로그 이메일 검색은 기존처럼 대소문자를 구분하지 않는다.
- 품목 선택 화면의 `/reference/hs-codes`는 **‘말’, ‘소’처럼 한 글자인 품목명**을 검색할 수 있다. 등록명·코드 일치/부분 일치와 하위 품목의 상위 분류 조회를 사용하며, ‘화자’를 ‘화장품’으로 추정하는 연관어·오타 보정은 검색어 길이에 관계없이 제안하지 않는다. HS 코드순 최대 5개 정렬은 유지한다. 채팅 내부 검색의 최소 두 글자 조건과 의미 검색 정책은 그대로다.
- 신규 구독은 발행 주기와 출력 양식 모두 미선택으로 시작한다. 둘 다 하나 이상 선택해야 저장할 수 있고, 기존 구독을 열면 저장된 선택을 유지한다. 서버의 빈 목록 거절 및 발행일·데이터 준비 조건은 유지한다.
- 최초 검수에서 가입 약관(A6-3)·동의 이력(E-3)·운영 국가/대륙(G-2)은 현황만 확인했다. 이후 사용자 요청으로 `origin/main`의 `540d773`을 병합하면서 가입 약관·동의 이력 구현도 함께 반영되었다. main의 필수 동의 검증·저장·알림 재동의 안내를 보존하고 이메일 정책과 구독 초기값 변경을 결합했다. 국가/대륙 데이터는 변경하지 않았다.

배포 순서: 기존 가입자의 로그인 안내를 공지한 뒤, 위 마이그레이션 계획을 확인하고 `--apply`를 실행한다. 같은 명령을 계획 모드로 다시 실행해 변경할 항목이 없는지 확인한 후 API를 배포한다. 호환 처리 덕분에 적용 전 로그인도 인덱스를 쓰지만, 적용 전에는 대소문자만 다른 신규 계정을 추가할 수 없다. 이번 작업은 실행 절차와 스크립트만 준비했으며 운영 적용·공지 발송은 수행하지 않았다.

공지 초안: “이메일 로그인에 대소문자 구분이 적용됩니다. 적용 전에 가입한 계정은 이메일을 모두 소문자로 입력해 주세요. 브라우저에 저장된 자동완성 주소도 확인해 주세요. 비밀번호는 변경되지 않습니다.” 로그인 화면에도 같은 기존 계정 안내를 표시한다.

## 2026-11-05 최종 결정 반영 (DEC-43/44/49)

이 절이 아래 초기 인계 기록의 계정 복구·키워드 관리자 정책보다 우선한다. 저장소의 API 계약과 상태표를 함께 갱신했다.

- **DEC-43 가입 여부 확인**: API-128은 이름·이메일 일치 여부만 `matches`, `message`로 반환한다. 화면 제목·버튼·로그인 링크는 “가입 여부 확인”으로 통일한다. API-129 아이디 안내 메일은 이 기능으로 대체하며 사용하지 않는다. 이름만으로 계정 후보를 찾거나 마스킹한 이메일을 제공하지 않는다.
- **DEC-44 임시 비밀번호 현행 유지**: 영문 대·소문자와 숫자를 모두 포함한 20자리 난수를 bcrypt 해시로 저장하고 기존 세션을 무효화한다. 별도 만료 시간은 없으며 재발급·사용자 비밀번호 변경 전까지 유효하다. 로그인 후 변경은 안내만 하고 강제하지 않는다. 계정 없음·이름 불일치·이용 불가·탈퇴·소셜 전용 계정은 모두 동일한 `403 RECOVERY_NOT_AVAILABLE`과 안내 문구를 반환한다. 성공 여부나 소요 시간까지 숨기는 방식은 아니며 API-128의 가입 여부 노출은 합의된 기능이다.
- API-130은 기존 이메일·IP 제한에 더해 이메일당 **600초에 1회, 최근 24시간 최대 5회**로 제한한다. `API_RECOVERY_COOLDOWN_SECONDS`, `API_RECOVERY_DAILY_MAX`로 조정하며 ISSUE/REISSUE는 한도를 공유한다. Redis Lua가 정규화한 이메일 해시별 쿨다운·이동 창을 원자적으로 예약한다. DB 커넥션을 얻기 전에 검사하며 불일치·발송 실패도 허용된 요청 횟수에 포함한다. 거절 시 한도를 늘리지 않고 `429 RECOVERY_RATE_LIMITED`와 실제 대기 시간 `Retry-After`를 반환한다. Redis 장애는 `503 REDIS_UNAVAILABLE`로 차단한다. 이 제한은 남용 빈도를 줄이지만 타인의 이름·이메일로 비밀번호를 교체할 수 있는 현행 정책 자체를 없애지는 않는다.
- **메일 운영**: Gmail 발신 계정의 `smtp.gmail.com:587`, STARTTLS, 앱 비밀번호를 사용한다. `API_SMTP_FROM`과 `API_SMTP_USERNAME`은 발신 Gmail 주소로 설정한다. 자격정보는 `.env`/배포 환경에서 주입하며 저장소·로그에 남기지 않는다. 예시는 `backend/.env.api.example`에 있다.
- **DB 저장과 발송 순서**: 비밀번호 해시·세션 버전 변경의 **DB 커밋 성공을 먼저 확인한 뒤** SMTP를 호출한다. DB 저장/커밋 예외가 나면 발송하지 않고 API 오류를 화면에 표시한다. SMTP 동안에는 사용자 행 잠금과 DB 커넥션을 유지하지 않는다. 명시적 메일 실패 시 새 해시·버전이 여전히 일치하는 경우에만 별도 트랜잭션으로 이전 해시·버전을 복구해 이후 변경을 덮어쓰지 않는다. DB와 SMTP는 원자적 처리가 아니므로 커밋 후 프로세스 종료, 메일 접수 응답 유실, 복구 DB 장애까지 보장하지는 않는다. 이 경우 운영 확인/재발급이 필요하다. 성공 응답은 SMTP 접수를 뜻하며 수신함 도착을 보장하지 않는다.
- SMTP는 표준 라이브러리만 사용하는 별도 프로세스에서 실행한다. `API_SMTP_TOTAL_TIMEOUT_SECONDS`(기본·최대 15초)가 DNS·연결·TLS·인증·전송 전체를 제한한다. 개별 소켓 제한은 `API_SMTP_TIMEOUT_SECONDS`다. 시간 초과 시 프로세스를 종료·회수하고 `503 MAIL_DELIVERY_FAILED`를 반환한다. Windows venv 실행기를 거치지 않고 실제 인터프리터를 실행하며 비밀값은 stdin 파이프로만 전달한다. DATA 접수 후 QUIT 응답은 기다리지 않는다.
- **키워드 검수 저장: 선택지 A**. 상태 컬럼을 추가하지 않고 최신 KEYWORD 감사 이력에서 검수 상태를 읽는다. 목록은 `ROW_NUMBER()`로 최신 이력을 묶어 조인하고 기사 건수도 집계해 조인한다(MySQL 8). 행별 상관 서브쿼리와 `CAST(... AS BINARY)`는 제거했다. 총 건수 쿼리는 기사·분야 집계를 제외한다. binary collation으로 대소문자가 다른 키워드를 구분한다.
- 감사 이력 `target_id`의 `utf8mb4_bin` collation과 `(target_type, target_id, created_at, audit_id)` 인덱스 마이그레이션을 준비했다. 기존 테이블·컬럼 수는 유지한다. `backend/migrations/063_admin_audit_lookup.sql`은 검토용이며 **운영 DB에는 아직 적용하지 않았다**. 대상 DB를 확인하고 `python -m backend.scripts.migrate_integration`으로 계획을 검토한 뒤 `--apply`로 반영한다. 이미 적용된 항목은 다시 변경하지 않는다. 앱 시작/요청 시 자동 DDL은 없다. 실제 운영 실행 계획·성능은 적용 후 확인한다.
- **DEC-49 새 기사부터 적용**: API-99는 `NEW_ONLY`만 받는다. 변경 전 기존 기사 분류를 `article.admin_meta_json.keyword_categories`에 고정하고, 이후 최초 적재되는 기사는 적재 시 캡처한 정책으로 분류를 고정한다. 일반 기사·단신·무역뉴스 적재 경로를 연결했다. 원문만 먼저 적재할 때는 빈 분류를 확정하지 않는다. 키워드 결과가 나중에 도착해도 최초 수신 당시의 정책으로 분류하며, 정제 결과가 실제로 빈 경우와 결과 미도착을 구분한다. 재적재는 고정된 분류를 덮어쓰지 않으며 관리자 기사 상세와 사용자 기사 분야 우선 정렬도 고정값을 따른다. 새 기사는 게시일이 아닌 **최초 적재** 기준이다. 저장 답변·리포트·기존 벡터는 변경하지 않으며 `CURRENT_LOOKUPS`와 `EXISTING_NOW`는 지원하지 않는다. 이 처리는 기존 JSON을 사용해 새 컬럼/테이블을 추가하지 않는다.
- **NEW_ONLY의 적용 경계**: 기존 미고정 기사를 변경 전에 고정하는 처리는 관리자 API-99의 분류 변경에만 적용한다. CSV 사전 적재(`keyword_topic_load`)는 이 고정 절차를 거치지 않는다. 따라서 이번 PR 이전에 적재되어 `keyword_categories`가 아직 없는 기사는 CSV로 사전 분류가 바뀌면 현재 조회의 분류도 소급해서 바뀐다. 이미 고정된 기사 분류는 유지된다.
- **최초 사전에 없는 키워드**: 최초 적재 정책 스냅샷에 키워드가 없거나 분야가 지정되지 않았다면 해당 기사의 그 키워드는 “분야 없음”으로 고정된다. 이후 사전에 키워드를 추가하거나 분야를 지정해도 기존 기사의 고정값은 바뀌지 않는다. 키워드 결과가 늦게 도착한 경우에도 최초 수신 정책을 기준으로 한다.
- **분류 고정 조회 비용**: 대상 기사 ID를 정렬·중복 제거한 후 500건 단위로 잠그고, 아직 고정되지 않은 기사의 태그를 `article_id IN (...)`으로 묶어 한 번에 읽어 기사별로 그룹화한다. 이미 고정된 기사에는 태그 재조회·UPDATE를 하지 않는다. 변경할 기사별 UPDATE와 변경 전체의 단일 트랜잭션은 유지하므로 실제 운영 데이터의 처리 시간·잠금 경합은 별도로 확인해야 한다.
- 키워드 지정·보류·해제는 사전과 감사 이력에 함께 저장한다. 수동 변경은 `synced_at=NULL`로 자동 덮어쓰기를 방지한다. 기본 대분류 8개·중분류 23개는 기존 `category_rules.TAX`를 사용한다. 조회 시 사전을 자동 적재하지 않는다.
- **분야 삭제·이관은 제공하지 않는다**. 삭제 버튼을 제거하고 API-105는 `422 FEATURE_NOT_AVAILABLE`을 반환한다. 관리자 생성 분야의 추가·이름 수정은 유지하며 기본/출처 미확인 분야는 보호한다. 처리 이력 조회는 유지한다.
- 회원 상세의 관심정보·구독·알림 설정 및 최근 로그인 KST `YYYY-MM-DD HH:mm:ss` 표시는 유지한다. 비밀번호·인증 정보는 반환하지 않는다. C-1 월말 통계는 준비 중을 유지한다. API-89 실행기 미연결로 재수집 버튼은 숨기며 연결 후 실패한 실행에만 노출한다. 운영 설정·기사 출처 관리·내용 해시 정책은 유지하고 실행 ID 정확 필터는 후속 작업으로 둔다.

## 구현 범위와 활성화 조건

- 총 130개 번호 중 삭제·예약 106~116은 경로를 만들지 않았다. 119개 경로를 등록했으며 90개는 처리 코드를, 29개는 명세의 보류·정책 미정·외부 실행기 미연결에 대한 명시적 오류 응답을 제공한다. 이것은 119개 기능 전체 완료를 뜻하지 않는다. 상세 상태는 [BACKEND_API_STATUS.md](BACKEND_API_STATUS.md)를 참조한다.
- 인증·관심·통계·기사·UN 조회·결과 스냅샷·대화 작업·리포트·구독·알림 조회/전달·일부 관리자 기능을 구현했다. 로컬 통합 검증 후 RDS에는 승인된 스키마 변경만 적용한다. API/worker/Redis 서버 배포는 별도다.
- 저장소는 PM 합의에 따라 기존 users/report/notification_setting 확장, api_snapshot/api_audit_event 신규, 인증 세션/요청 제한 Redis로 구현했다. 신규 테이블 2개와 기존 테이블 컬럼 11개를 명시적으로 적용한다. 036 SQL은 폐기된 제안이며 038 마이그레이션을 사용한다. 앱 시작/요청 시 자동 DDL은 없다.
- **가입 약관**: API-01은 만 14세 확인과 현재 이용약관·개인정보 동의 버전을 필수로 받아 `user_consent`에 저장한다. 약관은 `migrate_integration`으로 `option_type`을 늘린 뒤 `python -m backend.scripts.register_terms --apply`로 등록한다. 등록 전에는 가입이 `503 FEATURE_NOT_READY`다. 가입·로그인·내 계정 조회의 `user`는 같은 형태이며 `terms_consents`(가입 약관 동의 기록, 최신순)를 포함한다. 알림 설정 응답의 `consent_required`는 알림을 켰지만 현재 알림 약관에 동의하지 않은 상태다. 배포 순서와 등록 규칙은 [docs/terms](terms/README.md)를 본다.
- 활성 `REPORT_PERIOD`, `REPORT_TYPE` 및 승인된 `NOTIFICATION_TERMS`는 운영/데이터 담당자가 준비한다. 없는 옵션이나 약관을 가짜 값으로 생성하지 않는다. API-09에서 지원 주기를 확인한다. 요청형은 `RPT_ON_DEMAND`, 구독형은 `RPT_WEEKLY`, `RPT_MONTHLY`, `RPT_QUARTERLY` 옵션이 필요하다. 기존 DB에 요청형 옵션이 없거나 비활성이면 [요청형 리포트 옵션 SQL](../db/mysql/migrations/20261102_report_service_option.sql)을 수동 적용한다.
- ML 학습/예측, RAG 검색·생성·문장 검증은 담당자에게 남겼다. 기사 `summary`는 마스킹한 본문의 앞부분 발췌다. 채팅 의도는 `IntentProvider`의 기본 구현 `OpenAIIntentProvider`가 구조화된 JSON 슬롯으로 추출한다. 규칙 기반 의도/국가/기간 파서와 앞 세 단어 품목 탐색은 제거했다. 기본 모델은 `API_INTENT_MODEL=gpt-6-luna`이며 HS 임베딩 모델과 별개다.
- `async_job`은 사용하지 않는다. 채팅 실행은 기존 chat_message.result_json, 리포트 실행은 report.content_json의 내부 `_execution` 필드에 저장한다. 이번 PR 검수 반영으로 로컬 실행 상태 파일 의존성을 제거했다. 신규 테이블·컬럼 없이 JSON 규약을 확장하며, 다른 기능의 api_ 저장소 보완안과는 별개다.

## 설치와 실행

Python 3.11 이상에서 저장소 루트를 작업 디렉터리로 사용한다.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend/requirements-api.txt
python -m backend.scripts.check_api_schema
# INTEGRATION.md 절차로 038 마이그레이션과 Redis를 준비한 후:
python -m backend.scripts.create_api_admin
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --no-proxy-headers
# 별도 터미널
python -m backend.app.api.worker
```

관리자 생성 명령은 선택적인 최초 운영 설정이다. 실행할 때 비밀번호를 터미널에서 입력하며 기본 비밀번호가 없다. 기존 `admin@example.com`을 덮어쓰지 않는다. 이번 작업에서는 실행하지 않았다.

루트 `.env`에 `backend/.env.api.example`의 키를 설정한다. 기존 수집기의 `MYSQL_*`와 API의 `RDS_MYSQL_*`를 분리했다. `API_DB_TARGET=local`이면 기존 `MYSQL_*`를 사용한다. RDS 연결은 CA 인증서와 호스트명을 검증한다. `.env`/비밀번호는 커밋하지 않는다.

채팅 에이전트가 붙으면 API·worker는 `API_REDIS_URL`(`redis://:<비밀번호>@127.0.0.1:6379/0`)로 Redis에 접속한다. Redis는 `deploy/redis/docker-compose.yml`로 띄우고, 같은 비밀번호를 git에 올리지 않는 `deploy/redis/redis-auth.conf`에도 둔다([채팅 에이전트 설계](AGENT_DESIGN.md) D-07). 인증 세션·요청 제한(`api/redis_store.py`)이 이미 이 값과 `API_REDIS_PREFIX`를 읽으며, 채팅 에이전트도 같은 Redis를 쓴다(D-01).

로컬 HTTP 개발은 `API_COOKIE_SECURE=false`, HTTPS 배포는 `true`로 둔다. 프론트/백엔드의 호스트명을 localhost 또는 127.0.0.1 중 하나로 통일한다. 교차 사이트 배포는 같은 사이트 프록시 구성을 전제로 한다(SameSite=Lax). `API_CORS_ORIGINS`에 정확한 프론트 Origin을 지정한다. API/worker가 같은 파일 저장소에 접근해야 하며, Linux는 `API_REPORT_FONT`에 한글 TTF 글꼴을 지정한다.

- `/docs`, `/openapi.json`: API 요청 필드·인증·보류 이유.
- `/health/live`: 프로세스 확인.
- `/health/ready`: DB 연결, 앱 테이블·추가 컬럼, Redis 연결 확인. 전체 옵션/컬럼/원천 데이터 준비 완료를 뜻하지 않는다.
- `worker --once`: 구독 발행 조건 확인 후 작업 1건 처리.
- 파일은 `runtime/reports`에 보관하며 Git에서 제외한다. 임시 실패 파일 정리와 법정/운영 보존 정책은 이번 변경에 포함하지 않았다.

## 프론트 담당자 연동 계약

현재 src/live와 src/api/client.js가 아래 계약에 따라 실연동한다. 기존 목업 store는 진입점에서 제외했다. 공통 경로는 /api/v1이며 /docs에서 요청 계약을 확인한다.

모든 요청에 `credentials: include`를 사용한다. 로그인/가입의 `csrf_token`을 메모리에 보관하고 수정 요청의 `X-CSRF-Token`에 넣는다. 새로고침 뒤에는 `GET /users/me`가 `csrf_token`을 추가 반환하므로 세션을 복구할 수 있다(원 명세에 대한 호환 확장). 세션 쿠키 자체는 HttpOnly이다. snake_case를 그대로 사용하고 bigint 식별자를 Number로 변환하지 않는다. 배열 query는 `country_codes=US&country_codes=CN`처럼 반복 전달한다.

리포트는 `POST reports/preview` → 확인된 `preview_id`와 `confirm_conditions:true`로 `POST reports` → `GET reports/{id}/status` → 웹/파일 조회 순서다. 동일 제출의 재시도에는 같은 `Idempotency-Key`, 다른 제출에는 새 키를 사용한다. PDF/DOCX 선택 파일이 모두 완성된 뒤 READY가 된다. XLSX는 저장 표로 생성하며 표별 전체 1,000행 제한을 적용한다. DB의 기존 READY 제약에 맞춰 DOCX만 선택해도 내부 보관 PDF를 만들지만, 선택하지 않은 PDF 다운로드는 제공하지 않는다.

채팅은 세션 생성 → `client_message_id`를 포함한 메시지 POST → job 폴링 → NEEDS_INPUT이면 clarification 선택값 제출 순서다. 세션에서 조건이 확정된 뒤에도 같은 메시지 키의 재시도는 같은 job을 돌려준다. 미연결 ML/RAG 요청에는 성공한 모델 결과를 만들지 않는다. SQL은 일반 화면 응답에 없으며 XLSX의 정보 시트에 포함한다. 디버그 SQL은 `API_DEBUG_SQL=true`와 ADMIN 모두 필요하다.

질문 해석 실패, 공개 기간 오류, ML/RAG 연결 대기 및 범위 밖 안내는 마지막 성공 답변의 대화 조건을 지우지 않는다. 성공한 새 질문에서 `all_countries`/`all_products`를 명시하거나 기존 컨텍스트 해제 API를 호출하면 해당 범위를 해제한다. LLM의 `ranking_group`은 COUNTRY 또는 HS6이며 순위 대상이 불명확하면 재질문한다.

복수 품목은 표현마다 API-38 단일 선택을 반복한다. 매번 최신 `clarification_id`로 제출하며, 다음 품목이 남으면 같은 job이 다시 NEEDS_INPUT이 된다. 이미 선택한 품목은 기존 chat_message 실행 JSON에 보관하고 모든 표현을 확인한 뒤 조회한다. 따라서 첫 선택 응답만으로 완료를 가정하면 안 된다. 직접 선택(`hs_item`)도 같은 순서를 따른다. 복수 품목의 통계 답변은 품목별 표를 반환하고 각 표에 `hs_item`을 붙인다. HS4와 하위 HS6가 함께 선택되어도 합산 총계로 중복 계산하지 않는다.

API-19 및 채팅 추이 표에는 `previous_year_import_usd`(전년 수입액)를 추가했다. 전년 수출액과 각각의 집계 완료 여부로 검증하며, 검증된 월의 누락 거래는 0, 미검증 월은 null이다. 명시한 전년 비교는 방향에 맞는 금액·증감액·증감률을 답변에 표시한다. 전년 금액이 0이면 증감률을 계산하지 않으며, 비교 기간이 미검증이면 재입력을 안내한다.

503 `DATA_NOT_READY`/`FEATURE_NOT_READY`를 빈 목록이나 숫자 0으로 바꾸지 않는다. 해당 패널에 적재/연결 대기 안내를 표시한다. 409 버전 충돌은 최신 값을 재조회한 뒤 사용자가 다시 저장하게 한다. 보류 API-23/27은 422를 반환한다. RAG 미연결 기사 발췌를 AI 요약으로 표시하지 않는다.

### 프록시와 로그인 요청 제한

API_TRUSTED_PROXY_CIDRS에는 실제 리버스 프록시 IP/CIDR만 지정한다(기본 빈 값: 전달 헤더 무시). 앱이 실제 접속 상대를 검증할 수 있도록 uvicorn은 --no-proxy-headers로 실행한다. 신뢰된 상대의 X-Forwarded-For만 오른쪽부터 검사해 첫 비신뢰 주소를 사용한다. 프록시는 전달 헤더를 올바르게 덮어쓰거나 접속 주소를 추가해야 하며 공개 접속을 차단한 내부 프록시 구성에서 검증해야 한다. API_AUTH_IP_LIMIT은 IP당 분당 100회, API_AUTH_EMAIL_LIMIT은 정규화한 이메일당 분당 10회가 기본이다. 두 제한은 별도 해시 키로 기록한다. 프록시를 신뢰 목록에 넣지 않은 배포에서 실제 IP가 자동 복구되지는 않는다.

### HS 검색과 벡터 적재

API-11은 HS 코드·name_ko·original_name_ko 정확 일치 → Chroma hs_code 컬렉션의 HS2022의 요청 단위별 임베딩 후보 → 등록 품목명 부분 일치 보완 순으로 최대 5개를 반환한다. 여기서 정확 일치는 DB에 등록된 이름을 비교하는 의미이며 임의 동의어 사전을 만들지 않는다. 후보 코드는 다시 RDS에서 검증하고 자동 확정하지 않는다.

채팅은 별도 `chat_hs_search`로 HS6를 먼저 검색한다. HS6 정확 일치가 한 개이거나, 유효 벡터 후보의 1위 거리·1/2위 차이가 MEDIUM 조건을 만족하면 HS6 후보를 제시한다. 정확 일치가 여러 개이거나 신뢰도가 낮거나 HS6 후보가 없으면 HS4 검색으로 전환해 확인을 요청한다. 모든 후보는 사용자가 선택하며 API-12/38을 통한 직접 선택과 복수 품목 순차 확인을 유지한다. 명시된 4·6자리 코드는 해당 단위로 조회한다.

화면 API-11의 기본 검색 단위는 HS4다. 관심 품목 선택에서 6자리 코드를 입력하거나 품목명에 맞는 HS4가 없으면 `depth=6`으로 HS6 후보를 조회한다. 화면의 HS6 검색은 등록된 HS10 정식 명칭이 정확히 일치하면 그 HS6 부모를 후보로 반환한다(예: 소주 2208904000 → 220890). 채팅은 이 HS10 연결만으로 HS6를 자동 확정하지 않는다.

채팅의 HS6 의미 검색에는 HS 담당자가 같은 컬렉션에 적재한 HS2022/depth=6 벡터가 필요하다. 벡터가 없으면 DB 정확 일치나 HS4 확인·분류 탐색으로 진행한다. 이번 변경에서 HS6 데이터/벡터를 적재하지 않았으며 검색 단위가 달라도 동일 검색어의 질의 임베딩은 재사용한다.

모델은 기존 적재기의 text-embedding-3-large를 사용한다. API_HS_CHROMA_PATH(기본 chroma_data), OPENAI_API_KEY, API_HS_VECTOR_ENABLED를 설정한다. API_HS_MAX_DISTANCE의 기본 0.70은 후보 필터이며 정답 보장값이 아니다. 검색 품질 평가는 담당자 확인이 필요하다. 벡터 연결 실패 시 명시적인 warnings와 등록명 부분 일치만 반환한다. API 요청에서는 적재·컬렉션 생성 작업을 실행하지 않는다.

중복 경로였던 `backend/scripts/sync_hs_vectors.py`는 제거했다. 벡터 적재는 HS 담당의 `python -m backend.app.scheduler.jobs.hs_code_embed`로 일원화한다. 이 기존 작업은 자체 MYSQL_* 연결 설정을 사용하므로 운영 DB 대상은 담당자가 설정한다(비밀번호 포함 URL을 명령에 노출하지 않는다). API 서버는 컬렉션을 읽기만 한다. 과거 로컬 검증 데이터는 HS2 96개/HS4 1,228개이며, 배포 범위(HS2/4 또는 전체), 배포 경로, 갱신/재색인 담당은 별도 확정이 필요하다. 기존 적재기의 '새 ID만 추가' 동작도 유지하며 이번 수정에서 재적재하지 않았다.

검색어는 Unicode 정규화·공백 정리·대소문자 정규화 후 2~120자로 제한한다. 2자 미만은 임베딩 없이 빈 결과를 반환한다. API-11은 신뢰 프록시 검증을 거친 IP당 기본 분당 60회(`API_HS_IP_LIMIT`)로 제한하며, Redis 요청 제한 저장소를 사용한다. 캐시 적중도 요청 제한에 포함한다. 검색 결과와 질의 벡터는 각각 프로세스당 최대 256개, 300초 TTL로 캐시하며 같은 키의 동시 요청은 합친다. 여러 워커 사이의 캐시는 공유하지 않는다. 기준 데이터 재적재 후 API_HS_CACHE_VERSION을 변경/재시작하거나 TTL 만료를 기다린다. API 요청의 OpenAI 임베딩은 기본 timeout 3초, 자동 재시도 0회다(초기 라이브러리/Chroma 로딩 시간은 별도).

정확 일치는 confidence=EXACT, 유사 후보는 LOW 또는 MEDIUM이다. 기본 거리 상한 0.70 외에 1위 거리 0.45 이하와 1·2위 차이 0.08 이상을 모두 만족할 때만 MEDIUM으로 표시한다. 이는 정답 확률이 아니며 모든 결과는 requires_selection=true다. 비슷한 후보 또는 빈 결과에도 browse.url을 반환한다. API-12는 ROOT→HS2, HS2→HS4, HS4→HS6를 조회한다. API-38은 품목 되묻기에서 기존 choice_ids 대신 직접 선택한 hs_item을 받을 수 있으며 두 필드 동시 제출은 거절한다. 새 국가/품목/기간 슬롯과 응답 확장은 프론트 연동 시 함께 반영해야 한다.

신뢰도는 DB에 존재하는 HS2022/HS4 후보를 검증하고 코드 중복을 제거한 뒤 계산한다. 제외된 벡터 ID의 점수는 사용하지 않으며, 유효 후보가 하나뿐이거나 등록명 부분 일치만 있으면 LOW로 표시한다.

### 채팅 슬롯 추출과 프론트 연동

LLM 호출은 intent·국가의 원문 표현/한국어 이름·품목 원문 표현·기간·비교 기간·수출입 방향을 한 번에 추출한다. SQL이나 추론한 HS 코드를 받지 않는다. 원문 근거, country/hs_code 사전, 공개 기간을 서버에서 검증한다. 잘못된 국가·기간·숫자 품목, 응답 파싱 실패 등은 작업 FAILED 대신 재입력 안내(NO_DATA/NEEDS_REVIEW)로 돌려준다. 품목은 HS6 우선 후보 선택을 요청하며 후보가 없어도 분류에서 직접 선택할 수 있다. 일반적으로 같은 작업의 품목/관심 확인 후에는 기존 메시지 실행 JSON의 intent_slots를 재사용해 LLM을 재호출하지 않는다. 모델 실패 시 규칙 파서로 되돌아가지 않는다. 비교는 현재 고정 SQL이 지원하는 같은 기간의 전년 대비만 허용하고 다른 비교는 재입력을 요청한다.

국가명은 공백 제거·정규화 후 DB 이름 정확 일치가 우선이며, 없을 때 포함 일치 후보가 하나면 채택한다. 체코→체코공화국, 러시아→러시아 연방 등을 허용하되 콩고처럼 여러 후보면 전체 국가명을 다시 요청한다. 다른 유효 국가가 함께 있어도 모호한 국가를 조용히 버리지 않는다. SK/TV 등 모호한 두 글자 영문 약어 제외 정책은 유지한다. 숫자 HS4/HS6는 HS 접두어 없이도 HS2022 사전에 존재하면 인정한다. 연도·금액·수량 문맥은 코드로 오인하지 않으며 미등록 코드는 재입력을 안내한다.

임베딩 실패로 warnings가 붙은 검색 결과는 캐시하지 않는다. 다음 요청에서 즉시 다시 검색하며, 복구 후 정상 결과만 300초 캐시한다. 검색 결과 캐시는 HS4/HS6별로 구분한다.

기본 제공자는 store=False, timeout 기본 10초, SDK 자동 재시도 0회로 동작한다. 마스킹된 질문과 허용된 이전 조건만 전송하며 회원 정보나 DB 실적을 보내지 않는다. 팀 의도 모델은 db.intent_provider에 IntentProvider 구현을 주입하여 교체할 수 있다. ML/RAG 본문 생성은 연결하지 않았다. 구현 방식은 [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)를 참고했다.

현재 live/interests.jsx가 사전 API를 호출한다. 기존 목업 Hs4Search는 현재 진입점에 포함하지 않는다. 아래 규칙을 적용했다.

1. 검색어가 **2글자 이상이고 마지막 입력 후 300ms가 지난 때**에 API-11 호출. 한 조건만 만족하는 OR가 아니다.
2. 입력 변경/컴포넌트 해제 시 타이머와 이전 fetch를 취소하고, 취소 이후 도착한 응답도 버린다. 429는 즉시 반복 호출하지 않는다.
3. SIMILAR는 '비슷한 후보'로 표시하고 자동 확정하지 않는다. 결과 유무와 무관하게 browse.url의 분류 선택 버튼을 표시한다.
4. ROOT/HS2/HS4의 children을 순차 호출하여 직접 선택한다. 관심 품목은 기존처럼 HS6를 저장한다. 채팅 직접 선택은 API-38에 clarification_id와 hs_item을 제출한다.
5. 캐시는 백엔드가 담당하므로 별도의 프론트 캐시 구현이 필수는 아니다. 서버 캐시만으로 300ms 대기 UI가 구현되지는 않는다.

PR #34 적용 지점은 `frontend/src/components/pickers.jsx`의 `Hs4Search`다. 현재 `onConfirm(group)`의 `{code,name,items}` 구조를 유지하려면 API-11의 `{hs_code,name_ko}`를 code/name으로 매핑하고, HS4 선택 시 API-12의 HS6 목록을 `items: rows.map(row => [row.hs_code,row.name_ko])`로 전달한다. 로컬 hs4Groups를 실제 후보와 섞으면 없는 코드가 다시 노출되므로 API 연동 시 해당 mock 검색을 교체한다.

직접 선택 예: `POST /api/v1/chat/jobs/{job_id}/clarifications`에 `{"clarification_id":"...","hs_item":{"hs_code":"190230","hs_ver":"HS2022"}}`를 세션/CSRF 헤더와 함께 보낸다. 예시 코드는 실제 사전 존재 여부를 검증받는다.

### 환율과 알림 조회

fx_daily는 2026-10-27 기존 적재기로 RDS에 43개 통화/8,557건 적재되어 있다. 환율 조회는 통화 정보를 한 번 읽고 윈도 함수로 각 통화의 최근 두 영업일을 한 번에 조회한다. quote_unit(예: JPY 100)을 유지하고 직전 영업일 기준 등락을 계산한다. 실제 0과 미적재를 혼동하지 않으며 빈 통화는 계속 UNAVAILABLE이다. 이번 수정은 새 수집기를 추가하거나 정기 적재를 자동 설정하지 않는다.

알림은 차단 키워드·기사 노출 조건을 SQL EXISTS/JSON 조건으로 필터링하고 COUNT와 LIMIT/OFFSET으로 조회한다. 페이지의 기사·태그는 묶어서 읽으며, 상세 조회는 ID 조건을 적용한다. 팝업은 미확인 대상 최대 100개를 전달하고 확인 이후 남은 대상을 다음 호출에 제공한다. ⑩ 관리자 기사 목록의 영향 리포트 계산은 미확정 요청에 따라 그대로 유지한다.

## DB 및 담당자 연결 계약

### async_job 없는 채팅·리포트 실행

report.status/generation_key/retry_count, chat_message의 조건·결과 저장 구조를 재사용한다. conditions_json은 생성 조건으로 유지한다. content_json은 완료 결과와 내부 `_execution`을 함께 보관하도록 이번 검수 요청에 따라 확장했다. 이 필드는 원 DB 문서에 이미 확정된 필드가 아니며, 프론트 응답·문서 본문에는 노출하지 않는다.

| 기능 | 저장·처리 위치 |
|---|---|
| 채팅 접수·상태 조회 | 질문 USER 행을 접수 시 chat_message에 한 번 저장한다. API의 job_id는 해당 message_id다. 사용자 소유권은 chat_session과의 연결로 확인한다. |
| 대기·되묻기·재시작 | USER result_json의 `_execution`(version=1)에 요청 키, 확정 전 조건, 상태, 되묻기, 실행 토큰·유효 시각을 보관한다. 이 실행 메타데이터는 이번 구현의 JSON 확장이며 원문에 이미 정의된 필드라고 취급하지 않는다. 프론트에는 기존 Job 응답으로 변환하고 내부 메타데이터를 그대로 노출하지 않는다. |
| 완료 답변 | ASSISTANT content_masked/intent_json/result_json에 답변·확정 조건·결과를 저장한다. 같은 질문의 재시도·되묻기는 USER 행을 추가하지 않는다. |
| 리포트 작업 등록 | report의 QUEUED 행과 generation_key UNIQUE를 사용한다. 기존 요청형·구독형 리포트 ID를 그대로 사용한다. |
| 리포트 전체 상태 | report.status/retry_count가 기준이다. READY 결과는 재실행하지 않는다. |
| 리포트 실행 상태 | report.content_json._execution에 실행 토큰·유효 시각·시도 횟수·재시도 가능 시각·단계·오류를 저장한다. report 행의 상태와 같은 DB 트랜잭션으로 갱신한다. 과거 로컬 JSON/JSONL 파일은 읽지 않는다. |

리포트 작업 발견·선점은 RDS만 사용하므로 API/worker의 로컬 디렉터리가 달라도 실행할 수 있다. 완성 PDF/DOCX 다운로드에는 여전히 동일 경로의 공유 파일 볼륨이 필요하다. 파일 전달용 객체 저장소 연결은 별도 작업이다. `_execution` 없는 기존 미완료 report 행은 상태·retry_count·generation_key로 실행 정보를 구성해 재개한다. 원래 요청 조건이 현재 생성기 계약에 맞아야 하며, 과거 오류 내역을 복원하지는 않는다. 기존 worker를 종료하고 새 버전으로 전환한다.

중복 질문은 사용자 행 잠금과 요청 키 조회로, 동시 채팅 처리는 대화방→메시지 순서의 잠금으로 막는다. 워커는 기존 chat_message.result_json과 report.status/content_json에서 실행 상태와 재시도/만료 시각을 SQL로 거른 다음 테이블별 API_JOB_SCAN_SIZE(기본 100개)를 적용한다. 완료 이력과 아직 실행할 수 없는 작업은 후보 상한에 포함하지 않아 과거 이력을 100개씩 읽으며 2초씩 기다리지 않는다. 후보가 잠겨 있으면 다음 호출에서 그 뒤를 확인하고, 선점에 성공하면 해당 종류의 커서를 초기화해 오래된 만료 작업도 다시 확인한다. 전체 큐의 엄격한 FIFO는 보장하지 않는다. 실행 유효 시각은 10분이고 실행 중 대상 행 잠금은 유지한다. 재시작 시 만료 작업을 새 토큰으로 재개하며 이전 토큰의 저장은 거부한다. 테이블·컬럼 추가나 운영 DDL 적용은 없다. 채팅 JSON 필터 자체의 DB 스캔 비용은 남으므로 대규모 운영에서는 EXPLAIN/부하 측정 후 기존 테이블의 인덱스를 별도로 검토해야 한다.

리포트는 최초 실행을 포함해 API_REPORT_MAX_ATTEMPTS(기본 3회)까지 시도한다. 회차당 1회 즉시 재시도하고 다시 실패하면 DELAYED, API_REPORT_RETRY_DELAY_SECONDS(기본 300초) 후 다음 시도를 한다. 총 상한 도달·재시도 불가 오류는 FAILED로 종료하고 retryable=false를 반환한다. retry_count는 최초를 제외한 실제 재실행 횟수다. 대상이 살아 있는 NOT_FOUND 오류도 FAILED로 처리한다. 구독 예약 실패는 별도로 기록하고 5초 이후 재시도하며, 그동안 채팅·리포트 작업 처리는 계속한다. 작업 처리 루프 자체의 DB 오류는 기록 후 5초 뒤 재시도한다. --once에서도 예약 실패와 별개로 작업 처리를 한 번 시도한 다음 예약 오류를 종료 코드에 반영한다. 실제 MySQL 동시 워커/공유 볼륨 장애 검증은 별도로 필요하다.

이전 async_job 기반 코드를 운영했다면 자동 이전은 제공하지 않는다. 기존 미완료 작업을 확인하고 별도 이관 기준을 정해야 한다. 이번 작업에서는 실제 RDS에 작업을 등록하거나 데이터를 이관하지 않았다.

통계는 HS2022와 `country_role=COUNTRY`만 합산한다. 그 월 전체를 덮는 가장 최근 batch_run이 SUCCESS인 경우 공개한다. 실패/진행 중인 최신 실행이 있으면 그 기간을 제외한다. 수출·수입 공통 가용 범위를 메인 공개 기간으로 사용한다. 검증된 월 안에서 선택 국가·품목의 거래 행이 없으면 추이·순위 금액을 0으로 처리한다. 검증되지 않은 기간을 0으로 채우지 않으며 UN의 결측 표시 규칙은 별개로 유지한다. 검증 월·공개 범위·데이터 버전은 요청 Store 안에서 재사용하며 새 요청/스케줄 회차에서는 다시 확인한다.

API-24 변화 목록은 검증된 현재·비교 월의 거래 키 합집합을 비교한다. 누락 거래를 0으로 보아 신규 진출은 `new_entries`(성장률 null), 거래 중단은 `drops`(-100%)에 포함한다. 기존 최소 거래액·증감액 기준과 국가/품목 필터는 그대로 적용한다. 비교 월이 미검증이면 0으로 채우지 않고 오류를 반환한다. 성장률이 정의되지 않는 신규 거래를 API-22의 성장률 순위에 임의 삽입하지 않는다.

앱이 생성하는 datetime은 UTC이다. 원천 `DATE`는 통계월/기사일이다. 기존 적재 코드가 저장한 naive `DATETIME`의 시간대는 데이터 담당자가 확인해야 한다. 프론트 표시 시간대는 Asia/Seoul로 통일한다.

리포트 worker는 60초마다 활성 구독을 확인한다. 월간은 구독 저장 당시 최신월 이후 새로 검증된 월, 분기는 구독 시작 기준 이후 3개월 모두 검증된 미발행 분기, 주간은 지난주 기사·품목/키워드 일별 집계 배치가 모두 정상 완료된 경우 생성한다. 분기는 최신 공개월이 다음 달로 넘어가도 누락분을 복구하고 기존 발행 키로 중복을 방지한다. 월간/분기는 통계 테이블을 읽을 뿐 적재 작업을 호출하지 않는다. 주간은 통계 섹션이 없다. 기존 구독에 `filters_json.enabled_since`가 없으면 자동 과거 발행을 하지 않으며 설정 재저장이 필요하다. 가입 시점의 데이터보다 과거인 모든 월을 재발행하는 기능은 없다.

`event_delivery.deliver_event(store, event_id)`는 확정된 `alert_event`를 알림함에 전달하는 연결 함수다. 알림 ON·최신 약관 동의·활성 회원·관심/차단 조건과 중복을 검사한다. 구독 리포트 발행 사건은 리포트 worker가 만들며 요청형 리포트는 알림함 사건을 만들지 않는다.

주요 이슈(FR-204)는 `scheduler/jobs/major_issue_detect.py`가 매일 05:00·08:00(KST) 어제(T) 기준으로 판정해 `MAJOR_ISSUE` 사건을 저장하고 전달한다. 기사량 판정은 키워드·품목(HS6·HS4) 각각 최근 7일(T-6~T) ÷ 직전 8주 주평균(T-62~T-7 합계÷8) ≥ 3이고, 주평균이 정확히 0일 때만 분모를 1로 본다. 이 날짜 경계는 DEC-47 팀 확정 전 임시 적용값이다. 분류 판정은 최근 3일 KOTRA 시장뉴스 중 원천 분류가 통상·규제인 기사이며 기사마다 한 번만 만든다. 기간 안에 수집 성공 기록이 없는 날이 있으면 0건으로 보지 않고 그 기사량 판정을 건너뛴다(FR-906-05). 키워드는 `KOTRA_MARKET`·`KOTRA_SHORT_NEWS`, 품목은 `KOTRA_MARKET` 기록을 본다. **시장뉴스 일별 수집 잡은 아직 스케줄러에 없으므로** 수집이 매일 적재되기 전까지 기사량 판정은 건너뛰어진다. 급증 기사 알림(FR-203) 판정기는 구현하지 않았다.

프론트는 로그인한 일반 회원 화면에서 API-61을 응답의 `retry_after_seconds` 주기로 조회해 종류별 묶음을 팝업으로 보여 주고, 표시한 묶음을 API-62로 확인한다. 화면은 한 번에 한 묶음만 표시하므로 한 번 조회에 한 묶음만 발급하고, 다른 종류는 다음 조회에서 발급한다. 같은 회원이 여러 창에서 조회해도 한 알림은 한 창에만 발급한다. 발급한 묶음은 전달 ID 유효시간(5분) 동안 예약되어 다른 창의 조회에서 빠지고, 확인 없이 창이 닫히면 예약이 끝난 뒤 다시 발급한다. 확인한 알림은 다시 발급하지 않는다. 팝업 확인은 읽음 처리와 별개다. 이미 읽은 알림은 팝업으로 다시 보여 주지 않는다. 팝업을 끄거나 약관 동의가 없는 동안 쌓인 알림은 알림함에만 남고, 다시 켠 뒤 들어온 새 알림부터 팝업으로 보여 준다. 별도 컬럼이 없어 다시 켠 시각을 `popup_shown_at`에 함께 기록하므로, 이 값은 실제 표시뿐 아니라 "팝업 대상에서 제외됨"도 뜻한다. 알림 이동 대상은 그 회원이 열 수 있는 근거 기사 중에서 고르며, 대표 기사가 숨겨지면 다른 공개 기사로 연결한다. 관리자 화면의 종 숫자는 회원 알림(API-57)이 아니라 관리자 알림(API-80) 전체 중 안 읽은 건수다. 30초마다 1건만 조회해 전체 건수·최신 ID가 바뀌었을 때만 전체 ID를 다시 읽는다. API-80에 읽음 저장소가 없어 임시로 읽은 알림 ID를 브라우저 `localStorage`에 관리자별로 저장한다. 다른 PC·브라우저에는 이어지지 않으며, DB 보완이 정해지면 서버 저장으로 옮긴다. 주요 이슈 판정은 사건 키(event_key 고유 제약)를 원자적으로 등록한 작업만 전달한다. 정기 판정과 수동 재실행이 같은 사건에서 겹치면 늦은 쪽은 그 사건만 건너뛰고 나머지 판정을 계속한다. 사건을 처음 만들 때만 전달하므로 나중에 알림을 켠 회원에게 지난 사건을 보내지 않는다. 그날 마지막 회차(08:00)에도 기사량 판정을 건너뛰면 `MAJOR_ISSUE_DETECT`를 FAILED로 기록해 관리자 알림에 "주요 이슈 판정 미완료"로 표시한다. 관리자 알림의 리포트 분류(API-80 REPORT)는 FAILED인 구독 리포트의 식별정보(주기·대상 기간·리포트 번호)만 보여 준다. 리포트 발행 알림 제목·내용은 주기와 대상 기간을 포함한다. 주요 이슈 판정과 주간 리포트의 기사량은 일별 집계에서 비공개 기사를 뺀 공개 기사 기준이다(집계는 기사를 숨겨도 줄지 않는다). 주간 리포트의 급증 키워드는 구독 국가(없으면 전체)의 최근 7일과 직전 8주를 비교하고, 해당 기간 수집 완료 기록이 없으면 0건으로 표시하지 않고 비교 불가로 안내한다. 저장된 급증 판정은 그 기준일의 현재 공개 기사 수로 다시 계산해 기준 미달이면 빼고, 관심 범위는 그 판정의 기간·출처에 든 기사 전체로 판단한다. 키워드·품목 중 판단하지 못한 범위는 리포트에 안내한다. 주요 이슈는 그 주에 판정된 `alert_event`와, 판정 작업 실행 여부와 상관없도록 발행 시점에 직접 계산한 그 주 통상·규제 기사와 마지막 날 급증을 합쳐 싣는다. 주간 리포트의 기사 출처(웹 상세·DOCX·PDF 공통)는 기사 수 요약과 실제로 싣는 급증 키워드·주요 이슈(각 최대 10건)에 쓰인 기사의 매체만 한 번씩 적는다. 급증 항목은 최근 7일과 비교값인 직전 8주 기사를 건수 계산과 같은 대상·국가·공개 상태·회원 차단 조건으로 보고, 표시 건수 제한으로 빠진 항목의 출처는 넣지 않는다. 구독 리포트 실패 시각은 실행 기록의 `finished_at`을 쓴다.

무역 급증/급감 임계값은 확정 요구사항 기본값을 사용한다. 활성 `service_option.option_code=TRADE_CHANGE_THRESHOLDS`의 JSON으로 `minimum_amount_usd`, `minimum_delta_usd`, `surge_pct`, `drop_pct`, `major_pct`를 재설정할 수 있다. 행 생성/수정 도구는 추가하지 않았다. 일회성 추정은 적재된 `anomaly_code`만 읽고 재학습/재판정하지 않는다.

## 리포트 비교 조건과 결과표 재사용

API-43은 최종 월초·월말 및 최신 공개 월로 조정한 분석 기간을 기준으로 비교 기간을 확정한다. `MOM`은 한 달 분석의 직전 월이며 여러 달을 지정하면 `422 UNSUPPORTED_COMPARISON`으로 안내한다. `YOY`·`YOY_PERIOD`는 같은 분석 기간을 12개월 앞당긴다. 12개월을 넘는 분석에서 전년 동기 기간이 일부 겹치는 것은 허용한다. 명시한 비교 기간이 이 규칙과 다르면 400이며, 임의로 다른 기간으로 바꾸지 않는다. `CUSTOM`은 명시한 비교 기간이 필수이고 분석 시작 전에 끝나야 한다. `NONE`은 비교 기간을 받지 않고 비교 계산·증감률 문구를 생성하지 않는다. 월 단위 조정은 비교 기간에도 적용하며 조정 사항을 `applied_defaults`에 기록한다. 비교 데이터가 미수집이면 기존 정책대로 리포트에 경고와 null 증감률을 제공한다.

새 RESULT 스냅샷에는 공통 `Conditions` 필드만 저장한다. 리포트의 sections·formats·request_hash 등 내부 정보는 report 행에 보관한다. 이전 RESULT에 내부 필드가 섞여 있어도 API-43은 소유권·유효기간·종류를 확인한 후 분석 필드만 읽는다. 직접 입력에는 기존의 엄격한 필드 검증을 유지한다. `BOTH` 추이 결과를 수출로 임의 변환하지 않으며 `422 UNSUPPORTED_TRADE_FLOW`와 수출만 선택해 재조회하라는 안내를 반환한다. `IMPORT`도 기존 수출 전용 리포트 정책에 따라 422이다.

## 기존 백엔드 단계 검증 기록

```powershell
python -m unittest backend.tests.test_backend_api -v
python -m compileall -q backend/app/api backend/main.py backend/scripts
git diff --check
```

테스트 DB는 SQLite이며 `backend/tests/fixtures/api_schema.json`은 실제 RDS에서 읽은 컬럼 구조의 검증용 사본이다. 테스트 DB 생성 시 async_job은 제외하고 전체 API 테스트를 실행한다. 테스트 데이터는 메모리 DB에만 만든다. MySQL의 JSON CHECK·generated column·인덱스 잠금·동시 worker 경합은 SQLite가 재현하지 않으므로 배포 전 MySQL 통합 검증이 필요하다.

RDS에서 읽기 전용으로 연결/테이블 준비 상태/한글 HS 검색/국가/통계 공개기간/기사/환율 미준비 응답을 확인했다. 실제 회원 가입·파일 생성·관리자 변경은 RDS에서 실행하지 않았다. PR #34 프론트 전체 화면 연결·브라우저 E2E, SMTP/OAuth, ML/RAG는 테스트하지 않았다. DOCX 생성·표/치환/ZIP 검증은 했지만 LibreOffice가 없어 페이지 렌더링 검수는 못 했다. PDF는 렌더링해 확인했다.


최신 실연동 검증은 INTEGRATION.md 명령과 INTEGRATION_REVIEW.md 결과를 참조한다. 아래 기존 기록의 프론트/로컬 MySQL 미검증 항목은 이번 통합 검증으로 보완한다.


### Chromium 자동 준비 (2026-11-09 검수 반영)
`python -m backend.app.api.worker`는 시작할 때 PDF 변환과 같은 공통 함수로 Chromium의 실제 실행을 확인한다. Playwright 기본 headless 실행을 우선하고, headless 실행 파일이 없으며 전체 Chromium 실행 파일이 설치된 경우에만 해당 파일로 대체 실행한다. 실행 파일 누락일 때만 동일 Python으로 `python -m playwright install chromium`을 실행한 뒤 다시 실행을 확인한다. 그 외 실행 오류는 재설치로 감추지 않고 전달한다. 정상적인 워커 재시작에는 재다운로드하지 않는다. Playwright 업그레이드·새 사용자·새 컨테이너에서는 새 버전 설치가 필요할 수 있다. 네트워크가 없는 배포 환경은 이미지 빌드 단계에서 같은 설치 명령을 실행해 파일을 미리 포함한다.


### 리포트 다운로드 파일명 (2026-11-03)
리포트 XLSX·PDF·DOCX는 공통으로 `{국가명}_{시작일}~{종료일}_{품목명}_{분석내용}_리포트_{YYYYMMDD_hhmmss}.{확장자}`를 사용한다. 국가·품목을 생략하면 전체국가·전체품목이다. 등록명을 조회하고, 저장된 topic이 있으면 분석내용으로 쓰며 없으면 방향·지표로 수출액분석/수출증감분석/수출비중분석/수출순위분석 등을 표시한다. 여러 대상은 하이픈으로 연결하고 3개 초과는 외 N개로 줄인다. 긴 이름과 파일명 금지 문자를 정리한다. 서버 Content-Disposition의 UTF-8 이름을 프런트가 그대로 사용한다. 분석 결과표 단독 엑셀의 기존 파일명 정책은 별개다.

PDF 변환 실패는 설치 누락만을 뜻하지 않는다. report_pdf_failed 로그의 stage(BROWSER_START/PAGE_SETUP/HTML_LOAD/FONT_LOAD/PDF_RENDER)와 원래 Playwright 예외를 확인한다. 사용자 오류 문구도 단계별로 구분한다. 브라우저 파일이 있고 최소 PDF가 성공해도 특정 워커의 일시적 실행 실패가 있을 수 있으며, 재설치보다 같은 실행 환경에서 실제 리포트 재현과 워커 로그를 먼저 확인한다. 이미 재시도 상한에 도달한 FAILED 리포트는 환경 수정만으로 자동 재실행되지 않는다.

신규 리포트 실행 JSON은 report queue version=2로 등록한다. version=1만 조회하는 구형 워커가 최신 리포트를 가져가지 못하게 하며, 최신 워커는 기존 v1 및 실행 JSON 없는 과거 리포트도 복구할 수 있다. 처리 워커 host/pid/report_protocol은 내부 실행 JSON에 기록한다. 재시도 claim 시 이전 실패 오류를 지워 RUNNING 화면에 과거 오류가 계속 표시되지 않게 한다. PDF 오류 원인은 단계별 로그로 확인하며, 브라우저 재설치만으로 해결됐다고 간주하지 않는다.

리포트 파일명의 생성 시각은 completed_at을 한국 시간(KST)으로 변환한 값이며, 완료 시각이 없는 과거 자료는 created_at을 사용한다. 다운로드 시각은 사용하지 않아 같은 리포트의 XLSX·PDF·DOCX 및 재다운로드 파일명이 일관된다.

# 채팅 작업 실패 로그

워커의 `agent_structured_failed` 로그는 job_id·node·error_type과 함께 `attempt=현재/최대`, schema, validation을 기록한다. validation은 실패한 모델 이름(model), 실패 필드 경로·오류 종류·고정 문구 검증 사유(`state.SafeError`)를 최대 10건, 전체 오류 개수와 생략 여부로 남긴다. 예: `tasks.0.slots` / `value_error` / `절대 기간과 최근 개월 수를 동시에 지정할 수 없습니다`. 질문·프롬프트·응답 원문·인증 정보·임의 예외 메시지는 남기지 않으며 알 수 없는 필드명은 `<unknown>`으로 표시한다. 이전 로그에서 누락된 상세는 소급 복구할 수 없다.

# 채팅 컨텍스트 확인

저장소 루트 PowerShell에서 `.venv\Scripts\python.exe -m backend.scripts.inspect_chat_context 20`을 실행하면 `.env` 설정을 사용하여 해당 세션의 Redis 키, 남은 TTL, 진행 중 작업 ID, 최근 조건과 최대 5턴을 읽기 전용으로 출력한다. `20`은 브라우저 개발자 도구 Network의 채팅 messages 요청에 표시되는 세션 ID로 바꾼다. 접속 비밀번호는 출력하지 않는다. 출력에는 대화 내용이 포함되므로 공유 시 주의한다. `context: null`은 캐시 없음, TTL -2는 키 없음, active_job_id null은 진행 중 잠금 없음이다. 빈 summary는 검증에서 제외될 수 있으며 질문·조건 이력과 구분한다.
