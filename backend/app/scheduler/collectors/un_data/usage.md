# UN 데이터 사용법

전달 CSV를 처음 한 번 적재한 뒤, UN API의 발표 변경분으로 MySQL `un_data`를 갱신합니다.
SKN 공통 DB 모듈을 사용합니다. RAW·실행기록·체크포인트는 파일로만 보관하고 국가·HS 마스터는 조회만 합니다.

## 준비

저장소 루트에서 실행합니다. Python 3.10 이상(검증: 3.12).

```sh
python -m pip install -r backend/requirements.txt
python -m backend.app.scheduler.jobs.un_data_load --validate-only
```

`.env.un.sample`의 필요한 설정을 기존 루트 `.env`에 병합합니다.
`MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE`, `UN_COMTRADE_API_KEY`를 설정합니다.
실제 키·비밀번호는 커밋하지 않습니다. 환경변수가 `.env`보다 우선합니다.

DB 담당자가 `country`, `hs_code`, `un_data` 스키마와 `data/un_data/required_country.csv`·`required_hs.csv`의 부모 키를 확인해야 합니다.
`db/mysql/DB_스키마_읽기전용_조회.sql`은 대상 DB를 선택한 전용 연결에서 실행합니다.
`db/mysql/init/03_un_data.sql`은 기존 스키마 및 FK 문자셋·collation과 비교한 뒤 필요한 경우에만 적용합니다.
코드는 테이블이나 부모 마스터를 자동 생성하지 않습니다.

## 1. CSV 최초 적재 및 체크포인트 연결

먼저 테스트 DB로 실행합니다. 아래 `runtime` 대신 `runtime_test` 경로를 사용하세요.
테스트 완료 후 실제 대상 DB에서는 별도 상태 경로로 동일 순서를 실행합니다.

```sh
python -m backend.app.scheduler.jobs.un_data_refresh --initialize-csv --state-dir data/un_data/runtime
```

전달 CSV **76,191행**을 검증·적재·전수 대조한 뒤 체크포인트를 생성합니다. API는 호출하지 않습니다.
기준일 **2026-10-15**는 원본 수집 성공 기록과 CSV·수집 범위 해시로 확인했습니다.
다른 CSV·범위, 기존 체크포인트, 스냅샷과 다른 DB 내용은 초기화를 차단합니다.
DB commit 후 체크포인트 저장만 실패했다면 같은 명령으로 복구할 수 있습니다.
`un_data_load`의 일반 적재 명령은 체크포인트를 만들지 않으므로 위 명령을 사용하세요.

## 2. API 갱신 확인

초기 적재와 같은 DB 및 상태 경로를 사용합니다.

```sh
python -m backend.app.scheduler.jobs.un_data_refresh --api-env .env --state-dir data/un_data/runtime
```

마지막 정상 점검일 당일~실행일 발표 범위를 M/A 각각 조회합니다.
대상 국가·2022년 이후 통계기간의 변경 데이터셋을 재수집하고 RAW → 9컬럼 `un_data`로 변환·검증하여 교체합니다.
한국산 비중은 DB 생성 컬럼이 계산합니다. 정상 완료 시에만 점검일을 전진합니다.
확인: 터미널 `UN 갱신 완료`, 실행 폴더 `manifest.json`의 `DB_VERIFIED`, `checkpoint.json`의 `last_successful_check_date`.

## 3. 매월 운영

```sh
python -m backend.app.scheduler.main --un-api-env .env --un-state-dir data/un_data/runtime
```

시작 10초 후 1회 점검하고 **매월 1일 03:00 한국시간** 실행합니다. 기존 HS 작업과 같은 스케줄러 프로세스로 계속 실행합니다.
기존 `un_data_refresh --schedule`은 안내 오류로 종료합니다. 이전 UN 전용 프로세스가 실행 중이면 종료한 뒤 통합 스케줄러 하나를 운영하세요.
기본값은 루트 `.env`와 `data/un_data/runtime`입니다. 초기 적재·수동 갱신과 동일한 상태 경로를 사용하세요.
초기 체크포인트가 없으면 UN만 건너뛰며 자동으로 CSV를 적재하지 않습니다. 초기화 후 수동 갱신하거나 스케줄러를 재시작하세요.
UN 실행 실패는 기록하고 다른 작업은 계속합니다. 같은 프로세스의 시작·월별 점검은 중복을 막고, 별도 프로세스·수동 실행과의 동시 적재는 기존 파일/DB 잠금으로 차단합니다.
체크포인트를 다른 DB에 복사하지 말고 상태 폴더를 영속 보관하세요.
일부 범위가 실패하면 점검일을 유지하며 실패 범위를 다음 실행에서 재시도합니다. 진행 중인 회차에서는 성공한 API 요청 응답을 저장해 중간부터 이어받습니다. 기존 데이터셋 전체가 빈 응답이면 자동 삭제를 막습니다.
상태 유실·수집 범위 변경 시 임의 점검일을 넣지 말고 백업과 DB를 대조해 복구해야 합니다.

## DB 잠금과 금액 누락 기록

MySQL 잠금을 보유한 연결에서 초기 적재·갱신 트랜잭션을 수행합니다.
API 요청 전후와 적재 전·commit 직전·체크포인트 저장 전에 잠금 소유권을 확인합니다.
연결 종료·소유권 유실 시 실행을 중단합니다. DB commit 이후 파일 저장에 실패하면 기존 점검일부터 재시도합니다.
잠금 정리나 실패 기록 저장 오류가 발생해도 최초 작업 오류를 보존합니다.

실행 폴더의 `missing_amounts.json`은 다음 사유를 구분합니다.
- `KOREA_ROW_MISSING`: 해당 키의 한국 행이 없음.
- `KOREA_SAME_BASIS_AMOUNT_MISSING`: 한국 행은 있으나 선택된 CIF/FOB 기준 금액이 없음.

두 경우 모두 한국산 금액과 비중은 NULL을 유지하며, 다른 평가 기준 금액으로 대체하지 않습니다.
실제 관측값 0은 누락으로 기록하지 않습니다. 이 기록은 파일이며 DB 테이블을 추가하지 않습니다.

## 범위별 실패 및 재시도

국가·주기(M/A)·통계기간 하나를 처리 단위로 사용합니다. 각 범위의 모든 대상 품목을 검증한 뒤 하나의 트랜잭션으로 교체합니다.
일부 범위가 실패해도 다른 범위를 계속 처리합니다. 정상 범위는 새 데이터로 반영되고 실패 범위는 기존 데이터가 유지되므로, 재시도 완료 전에는 범위마다 갱신 시점이 다를 수 있습니다.

- `pending_datasets.json`: 처리 전 대상 목록을 저장하고, DB commit·검증 및 결과 기록이 완료된 범위만 제거합니다. 실패·중단된 범위는 다음 실행에서 재수집합니다.
- `runs/<실행>/datasets/<주기>_<기간>_<국가코드>/`: 범위별 RAW, 변환 CSV, 검증·금액 누락 기록과 `manifest.json`을 보관합니다.
- 전체 `manifest.json`의 `PARTIAL_FAILED`: 범위 실패가 있으며 전체 점검일은 그대로입니다. `succeeded`, `failed`, `pending`으로 결과를 확인합니다.

다음 실행은 기존 점검일부터 발표 내역을 다시 조회하고 저장된 재시도 목록을 합칩니다. 이번 발표 조회에 없는 실패 범위도 재시도하며, 같은 범위의 새 발표가 있으면 새 판본을 사용합니다. DB 반영에 성공한 동일 발표 시각·HS 판본은 다시 조회되어도 RAW 수집·적재를 건너뜁니다. 모든 대상이 성공해야 점검일이 전진합니다.
잠금 유실, 파일 저장 실패, API 공통 장애는 전체 실행을 중단합니다. commit 직후 중단된 경우에도 저장된 대상 목록을 통해 재처리합니다.
`checkpoint.json`과 `pending_datasets.json`을 함께 영속 보관하고 임의 수정·삭제하지 마세요. 기존 체크포인트는 그대로 사용할 수 있으며 첫 갱신 시 재시도 파일을 생성합니다.
수집은 같은 주기·기간·품목의 국가를 최대 100개씩 묶으며 검증·적재는 국가별로 유지합니다. 자동 재개 정책은 아래 절차를 따릅니다.

변환 CSV는 확인용으로 저장하며 적재 시 다시 읽지 않습니다. 메모리의 변환 결과에 같은 공통 검증을 적용한 뒤 적재합니다. 비중 계산은 변환·검증이 공유하며 DB의 생성 컬럼과 적재 후 대조합니다.

적재 후 대조는 ORM 객체 대신 필요한 9개 컬럼을 조회합니다. 초기·수동 적재는 입력 복합 키, 월별 교체는 잔여 행 검사까지 포함한 대상 범위를 조회하며, 부모 마스터도 입력에 필요한 키만 확인합니다. 키 목록은 100개씩 나누어 조회합니다.

## 성공한 발표 버전 재처리 방지

`pending_datasets.json`의 `completed_versions`에 국가·주기·기간별 마지막 성공 HS 판본과 `lastReleased` 전체 시각을 저장합니다. 상태 파일의 DB·수집 범위 해시가 일치할 때만 사용합니다. 같은 날짜라도 더 최신 시각이면 새로 처리합니다. 동일 시각의 판본 변경은 충돌로 보류합니다.
성공 표시는 DB commit·전수 검증·범위별 실행 기록 저장 이후에 재시도 목록 제거와 함께 원자적으로 저장합니다. 저장 실패 시 성공했다고 간주하지 않고 다시 처리합니다. 체크포인트만 저장하지 못했다면 성공 버전을 재처리하지 않고 점검일 저장을 재시도합니다.
전체 manifest의 `skipped`는 동일 성공 버전이라 건너뛴 범위 수입니다. 기존 파일에 성공 버전이 없으면 최초 1회는 재처리하여 기록을 생성합니다.
API 발표 목록 조회는 계속 수행합니다. 429 이후 같은 명령을 다시 실행하면 성공 범위를 건너뛰고 미처리 범위를 이어 처리합니다. 호출 예산과 자동 재개를 적용하며, 진행 중인 회차의 발표 조회 종료일은 고정합니다. 완료 후에는 새 발표일 범위를 조회합니다. API가 발표 시각·판본을 바꾸지 않고 내용을 수정하는 경우는 이 버전 비교만으로 감지하지 못합니다. 상태 파일은 DB와 함께 보존하며 외부에서 데이터를 변경한 경우 상태와 DB를 대조해 복구해야 합니다.

## API 공통 장애와 범위별 데이터 오류

API 공통 장애는 `ApiRequestError`로 전달하며 `kind`, `status_code`, `attempts`를 가집니다. 메시지에 특정 문구가 있는지로 분류하지 않습니다.
- 네트워크 오류·HTTP 408·5xx: 요청 하나에서 최대 3회 시도한 뒤에도 실패하면 전체 실행 중단. 다음 국가·기간에서 같은 장애를 반복 시도하지 않습니다.
- HTTP 401/403 및 그 밖의 비정상 HTTP 상태: 즉시 중단. 다른 4xx도 범위 데이터 문제라고 단정할 수 없으므로 보수적으로 중단합니다.
- JSON 파싱 또는 API 공통 응답 구조 오류: 즉시 중단. 원문 응답과 인증 키를 오류 메시지에 넣지 않습니다.
- 정상 응답 안의 국가·기간·금액·판본 등 범위 검증 오류: 해당 범위를 실패로 남기고 다른 범위를 계속 처리합니다. 발표 목록 단계도 범위를 식별할 수 있는 오류는 아래 절차로 분리합니다.

전체 `manifest.json`에 `error_type`, `error`, `api_error_kind`, `http_status`, `api_attempts`, `pending`, `request_count`를 기록합니다. 파일 저장이 가능할 때 기록되며, 미처리 대상과 이전 정상 점검일은 유지합니다. 장애 전 성공한 발표 버전은 복구 후 같은 실행 명령으로 재개할 때 건너뜁니다. 인증·데이터 오류를 제외한 일시적 API 장애는 아래 자동 재개 정책을 따릅니다.

## 발표 목록 오류 보류와 복구

미지원 HS 판본·동일 범위의 원본 판본 충돌·잘못된 발표 시각처럼 국가·주기·기간을 식별할 수 있는 목록 오류는 `pending_datasets.json`의 `catalog_errors`에 저장합니다. 실행 폴더의 `catalog_errors.json`에서도 확인할 수 있습니다. 같은 범위의 정상처럼 보이는 다른 항목이나 기존 재시도 데이터로 우회 적재하지 않습니다. 다른 정상 범위와 충돌하지 않는 기존 재시도 범위는 계속 처리합니다.
오류가 목록에서 사라져도 해제하지 않으며, 정상 발표 항목으로 교정되어야 일반 적재 대기 목록으로 이동합니다. 이후 적재가 실패하면 기존 재시도 목록에 남습니다. 발표 오류 또는 적재 미처리가 하나라도 있으면 정상 점검일을 전진하지 않습니다.
전체 manifest의 `catalog_failed`는 미해결 발표 오류 범위 수, `failed`는 이번 적재 과정에서 실패한 범위 수, `pending`은 적재 대기 수입니다. 발표 오류만 남아 있어도 전체 상태는 `PARTIAL_FAILED`입니다. 기존 성공 버전 건너뛰기는 정상 범위에 계속 적용합니다.
국가·기간을 식별할 수 없는 행, 조회 범위를 벗어난 응답, 목록 조회의 API 공통 장애는 전체 중단을 유지합니다. 같은 판본의 중복 발표는 가장 최근 발표 시각을 사용하며, 서로 다른 원본 판본은 임의로 고르지 않습니다.

CSV 검증은 파일을 연 `with` 블록 안에서 완료합니다. 검증 예외·traceback을 보관하더라도 파일을 닫으며, UTF-8 BOM 지원과 기존 검증 규칙은 유지합니다. 실제 Windows에서의 파일 교체·삭제는 별도 확인이 필요합니다.

## 오래된 발표로의 후퇴 방지

상태 파일의 `known_versions`는 범위별로 확인한 최신 발표 시각·판본을 보존합니다. 성공 여부를 뜻하지 않으며 성공 표시는 `completed_versions`, 미처리 상세는 `datasets`, 오류 보류는 `catalog_errors`로 관리합니다. 기존 상태 파일은 성공·대기 버전에서 최신 기준을 복원합니다.
새 발표가 저장된 최신 기준보다 오래되면 `skipped_stale`를 늘리고 무시합니다. 최신 재시도 대상이 있으면 이를 그대로 처리하며, 기존 발표 오류를 오래된 항목으로 해제하지 않습니다. 같은 시각·같은 판본의 성공은 `skipped`, 같은 시각·다른 판본은 오류 보류, 더 최신 시각은 갱신 대상입니다.
발표 시각은 UTC로 비교합니다. 오프셋 없는 시각은 UTC로 취급하고 `Z`·`+00:00`·다른 오프셋이 같은 순간을 나타내면 동등하게 비교합니다. 외부 API가 발표 시각을 과거로 교정한 경우 자동 반영하지 않으므로 담당자가 원본과 상태를 확인해야 합니다.

## 작업 오류와 오류 기록 저장 실패가 겹치는 경우

범위 검증이 실패한 뒤 실패 manifest·재시도 상태·실패 실행 요약 저장에서도 오류가 발생하면 즉시 실행을 중단합니다. 최초 작업 예외를 최상위로 유지하고 저장 예외를 원인(`__cause__`)으로 연결합니다. 전체 manifest를 저장할 수 있으면 원래 `error_type`·`error`와 별도로 `recording_errors`에 저장 경로·오류 유형·메시지를 기록합니다.
디스크 장애로 모든 기록 파일을 쓸 수 없으면 터미널 로그에서 원래 작업 오류와 저장 오류를 확인해야 합니다. 정상 점검일은 유지하고, 저장 장애 복구 후 같은 상태 경로로 재실행합니다.


## 일시적인 HTTP 429 대응

요청 시작 간격은 기본 2초입니다. 429는 Retry-After(초 또는 HTTP 날짜)에 1초 여유를 더해 같은 요청을 최대 3회 시도합니다. 안내가 없거나 잘못됐으면 3초·5초 대기를 사용합니다. 한 번의 대기가 60초를 넘으면 안내 시간을 줄이지 않고 즉시 중단합니다. 401/403은 즉시 중단합니다.
응답 파일 옆 `.retry.jsonl`에 시도·대기 시간과 숫자형 제한 정보를 남깁니다. 최종 실패 manifest에는 `api_retry_info`를 기록합니다. 인증 키·응답 원문은 기록하지 않습니다. 이 재시도는 요청 내부에서 수행하며 각 HTTP 시도는 실행당 호출 예산에 포함합니다. 실행 전체의 재개는 아래 정책으로 별도 관리합니다.


UN advisory lock 전용 연결은 잠금을 얻기 전에 연결 풀에서 분리합니다. 따라서 연결 폐기가 취소되더라도 후속 close는 풀 반환 대신 물리 연결 종료를 수행합니다. UN 작업마다 전용 연결을 사용하며 SKN 공통 DB 모듈의 풀 설정은 변경하지 않습니다.


## 묶음 수집·실행 예산·자동 재개

- 묶음 응답에서 국가를 식별할 수 있는 중복·금액 오류는 해당 국가만 실패로 기록합니다. 응답 상한 도달이나 국가 식별 불가는 전체 중단합니다.
- API 재시도 중 호출 예산이 끝나면 마지막 API 오류를 유지하여 2시간·최대 3회 재개 정책을 적용합니다. 장애 없이 예산만 소진했을 때 5분 뒤 재개합니다.
- 기본 HTTP 예산은 실행당 300회입니다. 목록·품목·요청 내부 재시도를 모두 포함하며 캐시 읽기는 제외합니다. 일일 할당량 설정과는 별개입니다.
- 예산 소진은 5분 뒤 재개합니다. 네트워크·HTTP 408/429/5xx 지속 장애는 2시간 뒤 최대 3회 자동 재개합니다(최초 실행과 별도). 서버 Retry-After가 더 길면 그 시간 이상 기다립니다.
- 401/403·기타 비정상 HTTP·응답 구조·데이터 검증·DB/파일 오류는 자동 반복하지 않습니다. 원인을 확인한 후 수동 재실행하세요.
- `continuation.json`에 회차·고정 발표 조회 범위·재개 사유·다음 시각·API 재개 횟수를 저장합니다. `continuations/`에는 요청별 성공 응답과 묶음 계획을 보관합니다. 기존 checkpoint/pending 파일과 함께 영속 보존해야 합니다.
- 스케줄러의 `un_data_resume` 작업이 매분 기한을 확인하므로 실제 재개는 지정 시각 이후 최대 약 1분 지연될 수 있습니다. 대기 중 DB/API 연결·잠금을 보유하지 않습니다. 스케줄러가 꺼져 있으면 자동 실행하지 않으며 재시작 시 저장된 기한을 확인합니다.
- `RETRY_EXHAUSTED`는 자동 재개 3회를 소진한 상태입니다. 담당자가 장애 복구를 확인한 후 `python -m backend.app.scheduler.jobs.un_data_refresh --state-dir <동일 경로> --api-env <설정 파일> --resume-now`로 즉시 재개하고 횟수를 초기화할 수 있습니다.
- DB 반영·검증 완료 범위는 건너뜁니다. 수집 중단 범위는 저장된 성공 요청을 사용하되 해당 국가의 모든 품목이 준비된 뒤 트랜잭션으로 반영합니다. 성공 응답 저장 자체가 실패했으면 그 요청은 다시 호출될 수 있습니다.
- 데이터 오류를 수정해 재실행하는 경우에는 오래된 오류 응답을 재사용하지 않도록 새 회차로 조회합니다. 이미 성공한 발표 버전 표시는 유지합니다. 장시간 중단한 회차를 완료하면 이후 발표분도 5분 뒤 새 회차에서 확인합니다.
