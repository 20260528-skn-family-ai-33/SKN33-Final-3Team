# UN 데이터 사용법

전달 CSV를 처음 한 번 적재한 뒤, UN API의 발표 변경분으로 MySQL `un_data`를 갱신합니다.
SKN 공통 DB 모듈을 사용합니다. RAW·실행기록·체크포인트는 파일로만 보관하고 국가·HS 마스터는 조회만 합니다.

## 준비

저장소 루트에서 실행합니다. Python 3.10 이상(검증: 3.12).

```sh
python -m pip install -r backend/requirements.txt
python -m backend.app.scheduler.jobs.un_data_load --validate-only
```

`.env.un.sample`의 필요한 설정을 기존 루트 `.env`에 병합합니다.
`MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE`, `UN_COMTRADE_API_KEY`를 설정합니다.
실제 키·비밀번호는 커밋하지 않습니다. 환경변수가 `.env`보다 우선합니다.

DB 담당자가 `country`, `hs_code`, `un_data` 스키마와 `data/un_data/required_country.csv`·`required_hs.csv`의 부모 키를 확인해야 합니다.
`db/mysql/DB_스키마_읽기전용_조회.sql`은 대상 DB를 선택한 전용 연결에서 실행합니다.
`db/mysql/init/03_un_data.sql`은 기존 스키마 및 FK 문자셋·collation과 비교한 뒤 필요한 경우에만 적용합니다.
코드는 테이블이나 부모 마스터를 자동 생성하지 않습니다.

## 1. CSV 최초 적재 및 체크포인트 연결

먼저 테스트 DB로 실행합니다. 아래 `runtime` 대신 `runtime_test` 경로를 사용하세요.
테스트 완료 후 실제 대상 DB에서는 별도 상태 경로로 동일 순서를 실행합니다.

```sh
python -m backend.app.scheduler.jobs.un_data_refresh --initialize-csv --state-dir data/un_data/runtime
```

전달 CSV **76,191행**을 검증·적재·전수 대조한 뒤 체크포인트를 생성합니다. API는 호출하지 않습니다.
기준일 **2026-10-15**는 원본 수집 성공 기록과 CSV·수집 범위 해시로 확인했습니다.
다른 CSV·범위, 기존 체크포인트, 스냅샷과 다른 DB 내용은 초기화를 차단합니다.
DB commit 후 체크포인트 저장만 실패했다면 같은 명령으로 복구할 수 있습니다.
`un_data_load`의 일반 적재 명령은 체크포인트를 만들지 않으므로 위 명령을 사용하세요.

## 2. API 갱신 확인

초기 적재와 같은 DB 및 상태 경로를 사용합니다.

```sh
python -m backend.app.scheduler.jobs.un_data_refresh --api-env .env --state-dir data/un_data/runtime
```

마지막 정상 점검일 당일~실행일 발표 범위를 M/A 각각 조회합니다.
대상 국가·2022년 이후 통계기간의 변경 데이터셋을 재수집하고 RAW → 9컬럼 `un_data`로 변환·검증하여 교체합니다.
한국산 비중은 DB 생성 컬럼이 계산합니다. 정상 완료 시에만 점검일을 전진합니다.
확인: 터미널 `UN 갱신 완료`, 실행 폴더 `manifest.json`의 `DB_VERIFIED`, `checkpoint.json`의 `last_successful_check_date`.

## 3. 매월 운영

```sh
python -m backend.app.scheduler.main --un-api-env .env --un-state-dir data/un_data/runtime
```

시작 10초 후 1회 점검하고 **매월 1일 03:00 한국시간** 실행합니다. 기존 HS 작업과 같은 스케줄러 프로세스로 계속 실행합니다.
기존 `un_data_refresh --schedule`은 안내 오류로 종료합니다. 이전 UN 전용 프로세스가 실행 중이면 종료한 뒤 통합 스케줄러 하나를 운영하세요.
기본값은 루트 `.env`와 `data/un_data/runtime`입니다. 초기 적재·수동 갱신과 동일한 상태 경로를 사용하세요.
초기 체크포인트가 없으면 UN만 건너뛰며 자동으로 CSV를 적재하지 않습니다. 초기화 후 수동 갱신하거나 스케줄러를 재시작하세요.
UN 실행 실패는 기록하고 다른 작업은 계속합니다. 같은 프로세스의 시작·월별 점검은 중복을 막고, 별도 프로세스·수동 실행과의 동시 적재는 기존 파일/DB 잠금으로 차단합니다.
체크포인트를 다른 DB에 복사하지 말고 상태 폴더를 영속 보관하세요.
일부 범위가 실패하면 점검일을 유지하며 실패 범위를 다음 실행에서 재시도합니다. API 요청별 이어받기는 없습니다. 기존 데이터셋 전체가 빈 응답이면 자동 삭제를 막습니다.
상태 유실·수집 범위 변경 시 임의 점검일을 넣지 말고 백업과 DB를 대조해 복구해야 합니다.

## 검증 및 범위

```sh
python -m unittest discover backend/tests -v
```

운영 DB 접속정보가 없어 실제 스키마·마스터 호환성은 미검증입니다.
로컬 MySQL 검사에는 임시 DB와 테스트 부모 키를 사용했으며 후속 API 연결 검증은 모의 응답을 포함합니다.
원본 데이터와 SKN 공통 DB 코드는 변경하지 않았습니다.

## DB 잠금과 금액 누락 기록

MySQL 잠금을 보유한 연결에서 초기 적재·갱신 트랜잭션을 수행합니다.
API 요청 전후와 적재 전·commit 직전·체크포인트 저장 전에 잠금 소유권을 확인합니다.
연결 종료·소유권 유실 시 실행을 중단합니다. DB commit 이후 파일 저장에 실패하면 기존 점검일부터 재시도합니다.
잠금 정리나 실패 기록 저장 오류가 발생해도 최초 작업 오류를 보존합니다.

실행 폴더의 `missing_amounts.json`은 다음 사유를 구분합니다.
- `KOREA_ROW_MISSING`: 해당 키의 한국 행이 없음.
- `KOREA_SAME_BASIS_AMOUNT_MISSING`: 한국 행은 있으나 선택된 CIF/FOB 기준 금액이 없음.

두 경우 모두 한국산 금액과 비중은 NULL을 유지하며, 다른 평가 기준 금액으로 대체하지 않습니다.
실제 관측값 0은 누락으로 기록하지 않습니다. 이 기록은 파일이며 DB 테이블을 추가하지 않습니다.

## 범위별 실패 및 재시도

국가·주기(M/A)·통계기간 하나를 처리 단위로 사용합니다. 각 범위의 모든 대상 품목을 검증한 뒤 하나의 트랜잭션으로 교체합니다.
일부 범위가 실패해도 다른 범위를 계속 처리합니다. 정상 범위는 새 데이터로 반영되고 실패 범위는 기존 데이터가 유지되므로, 재시도 완료 전에는 범위마다 갱신 시점이 다를 수 있습니다.

- `pending_datasets.json`: 처리 전 대상 목록을 저장하고, DB commit·검증 및 결과 기록이 완료된 범위만 제거합니다. 실패·중단된 범위는 다음 실행에서 재수집합니다.
- `runs/<실행>/datasets/<주기>_<기간>_<국가코드>/`: 범위별 RAW, 변환 CSV, 검증·금액 누락 기록과 `manifest.json`을 보관합니다.
- 전체 `manifest.json`의 `PARTIAL_FAILED`: 범위 실패가 있으며 전체 점검일은 그대로입니다. `succeeded`, `failed`, `pending`으로 결과를 확인합니다.

다음 실행은 기존 점검일부터 발표 내역을 다시 조회하고 저장된 재시도 목록을 합칩니다. 이번 발표 조회에 없는 실패 범위도 재시도하며, 같은 범위의 새 발표가 있으면 새 판본을 사용합니다. 정상 범위도 발표 조회에 다시 잡히면 재처리될 수 있습니다. 모든 대상이 성공해야 점검일이 전진합니다.
잠금 유실, 파일 저장 실패, API 인증·할당량 오류(401/403/429)는 전체 실행을 중단합니다. commit 직후 중단된 경우에도 저장된 대상 목록을 통해 재처리합니다.
`checkpoint.json`과 `pending_datasets.json`을 함께 영속 보관하고 임의 수정·삭제하지 마세요. 기존 체크포인트는 그대로 사용할 수 있으며 첫 갱신 시 재시도 파일을 생성합니다.
재시도는 다음 수동 실행 또는 정기 실행에서 수행하며 별도 즉시 재시도 작업은 없습니다. 국가별 수집으로 국가 묶음 조회보다 API 요청 수가 늘어날 수 있습니다.

변환 CSV는 확인용으로 저장하며 적재 시 다시 읽지 않습니다. 메모리의 변환 결과에 같은 공통 검증을 적용한 뒤 적재합니다. 비중 계산은 변환·검증이 공유하며 DB의 생성 컬럼과 적재 후 대조합니다.

적재 후 대조는 ORM 객체 대신 필요한 9개 컬럼을 조회합니다. 초기·수동 적재는 입력 복합 키, 월별 교체는 잔여 행 검사까지 포함한 대상 범위를 조회하며, 부모 마스터도 입력에 필요한 키만 확인합니다. 키 목록은 100개씩 나누어 조회합니다.
