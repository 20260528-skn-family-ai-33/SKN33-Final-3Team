# UN 데이터 사용법

전달 CSV를 처음 한 번 적재한 뒤, UN API의 발표 변경분으로 MySQL `un_data`를 갱신합니다.
SKN 공통 DB 모듈을 사용합니다. RAW·실행기록·체크포인트는 파일로만 보관하고 국가·HS 마스터는 조회만 합니다.

## 준비

저장소 루트에서 실행합니다. Python 3.10 이상(검증: 3.12).

```sh
python -m pip install -r backend/requirements.txt
python -m backend.app.scheduler.jobs.un_data_load --validate-only
```

루트 `.env.sample`의 `UN 데이터 적재 설정`과 MySQL 항목을 참고해 루트 `.env`에 설정합니다.
`MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE`, `UN_COMTRADE_API_KEY`를 설정합니다.
실제 키·비밀번호는 커밋하지 않습니다. 환경변수가 `.env`보다 우선합니다.

DB 담당자가 `country`, `hs_code`, `un_data` 스키마와 `data/un_data/required_country.csv`·`required_hs.csv`의 부모 키를 확인해야 합니다.
`db/mysql/DB_스키마_읽기전용_조회.sql`은 대상 DB를 선택한 전용 연결에서 실행합니다.
`db/mysql/init/03_un_data.sql`은 기존 스키마 및 FK 문자셋·collation과 비교한 뒤 필요한 경우에만 적용합니다.
코드는 테이블이나 부모 마스터를 자동 생성하지 않습니다.

## 1. CSV 최초 적재 및 체크포인트 연결

먼저 테스트 DB로 실행합니다. 아래 `runtime` 대신 `runtime_test` 경로를 사용하세요.
테스트 완료 후 실제 대상 DB에서는 별도 상태 경로로 동일 순서를 실행합니다.

```sh
python -m backend.app.scheduler.jobs.un_data_refresh --initialize-csv --state-dir data/un_data/runtime
```

전달 CSV **67,550행**을 검증·적재·전수 대조한 뒤 체크포인트를 생성합니다. API는 호출하지 않습니다.
기준일 **2026-10-15**는 원본 수집 성공 기록과 CSV·수집 범위 해시로 확인했습니다.
다른 CSV·범위, 기존 체크포인트, 스냅샷과 다른 DB 내용은 초기화를 차단합니다.
DB commit 후 체크포인트 저장만 실패했다면 같은 명령으로 복구할 수 있습니다.
`un_data_load`의 일반 적재 명령은 체크포인트를 만들지 않으므로 위 명령을 사용하세요.

## 2. API 갱신 확인

초기 적재와 같은 DB 및 상태 경로를 사용합니다.

```sh
python -m backend.app.scheduler.jobs.un_data_refresh --api-env .env --state-dir data/un_data/runtime
```

마지막 정상 점검일 당일~실행일 발표 범위를 M/A 각각 조회합니다.
대상 국가·2022년 이후 통계기간의 변경 데이터셋을 재수집하고 RAW → 9컬럼 `un_data`로 변환·검증하여 교체합니다.
한국산 비중은 DB 생성 컬럼이 계산합니다. 정상 완료 시에만 점검일을 전진합니다.
확인: 터미널 `UN 갱신 완료`, 실행 폴더 `manifest.json`의 `DB_VERIFIED`, `checkpoint.json`의 `last_successful_check_date`.

## 3. 매월 운영

```sh
python -m backend.app.scheduler.main --un-api-env .env --un-state-dir data/un_data/runtime
```

시작 10초 후 1회 점검하고 **매월 10일 03:00 한국시간** 실행합니다. 기존 HS 작업과 같은 스케줄러 프로세스로 계속 실행합니다.
기존 `un_data_refresh --schedule`은 안내 오류로 종료합니다. 이전 UN 전용 프로세스가 실행 중이면 종료한 뒤 통합 스케줄러 하나를 운영하세요.
기본값은 루트 `.env`와 `data/un_data/runtime`입니다. 초기 적재·수동 갱신과 동일한 상태 경로를 사용하세요.
초기 체크포인트가 없으면 UN만 건너뛰며 자동으로 CSV를 적재하지 않습니다. 초기화 후 수동 갱신하거나 스케줄러를 재시작하세요.
UN 실행 실패는 기록하고 다른 작업은 계속합니다. 같은 프로세스의 시작·월별 점검은 중복을 막고, 별도 프로세스·수동 실행과의 동시 적재는 기존 파일/DB 잠금으로 차단합니다.
체크포인트를 다른 DB에 복사하지 말고 상태 폴더를 영속 보관하세요.
일부 범위가 실패하면 점검일을 유지하며 실패 범위를 다음 실행에서 재시도합니다. 진행 중인 회차에서는 성공한 API 요청 응답을 저장해 중간부터 이어받습니다. 기존 데이터셋 전체가 빈 응답이면 자동 삭제를 막습니다.
상태 유실·수집 범위 변경 시 임의 점검일을 넣지 말고 백업과 DB를 대조해 복구해야 합니다.


운영 DB 접속정보가 없어 실제 스키마·마스터 호환성은 미검증입니다.
2026-10-19 로컬 MySQL에서는 팀 DDL 6개와 실제 국가 seed를 고유 임시 DB에 적용하고 67,550행 전수 대조를 통과했습니다. HS 부모 15개는 임시 DB 전용 테스트 fixture이며, 실제 운영 HS 마스터와 최신 API 전체 수집은 미검증입니다.
UN 적재는 공통 부모 마스터를 변경하지 않습니다. 전달 CSV에는 앞서 정한 HS2022 전용 필터가 적용되어 있습니다.

## DB 잠금과 금액 누락 기록

MySQL 잠금을 보유한 연결에서 초기 적재·갱신 트랜잭션을 수행합니다.
API 요청 전후와 적재 전·commit 직전·체크포인트 저장 전에 잠금 소유권을 확인합니다.
연결 종료·소유권 유실 시 실행을 중단합니다. DB commit 이후 파일 저장에 실패하면 기존 점검일부터 재시도합니다.
잠금 정리나 실패 기록 저장 오류가 발생해도 최초 작업 오류를 보존합니다.

실행 폴더의 `missing_amounts.json`은 다음 사유를 구분합니다.
- `KOREA_ROW_MISSING`: 해당 키의 한국 행이 없음.
- `KOREA_SAME_BASIS_AMOUNT_MISSING`: 한국 행은 있으나 선택된 CIF/FOB 기준 금액이 없음.

두 경우 모두 한국산 금액과 비중은 NULL을 유지하며, 다른 평가 기준 금액으로 대체하지 않습니다.
실제 관측값 0은 누락으로 기록하지 않습니다. 이 기록은 파일이며 DB 테이블을 추가하지 않습니다.

## 범위별 실패 및 재시도

국가·주기(M/A)·통계기간 하나를 처리 단위로 사용합니다. 각 범위의 모든 대상 품목을 검증한 뒤 하나의 트랜잭션으로 교체합니다.
일부 범위가 실패해도 다른 범위를 계속 처리합니다. 정상 범위는 새 데이터로 반영되고 실패 범위는 기존 데이터가 유지되므로, 재시도 완료 전에는 범위마다 갱신 시점이 다를 수 있습니다.

- `pending_datasets.json`: 처리 전 대상 목록을 저장하고, DB commit·검증 및 결과 기록이 완료된 범위만 제거합니다. 실패·중단된 범위는 다음 실행에서 재수집합니다.
- `runs/<실행>/datasets/<주기>_<기간>_<국가코드>/`: 범위별 RAW, 변환 CSV, 검증·금액 누락 기록과 `manifest.json`을 보관합니다.
- 전체 `manifest.json`의 `PARTIAL_FAILED`: 범위 실패가 있으며 전체 점검일은 그대로입니다. `succeeded`, `failed`, `pending`으로 결과를 확인합니다.

다음 실행은 기존 점검일부터 발표 내역을 다시 조회하고 저장된 재시도 목록을 합칩니다. 이번 발표 조회에 없는 실패 범위도 재시도하며, 같은 범위의 새 발표가 있으면 새 판본을 사용합니다. DB 반영에 성공한 동일 발표 시각·HS 판본은 다시 조회되어도 RAW 수집·적재를 건너뜁니다. 모든 대상이 성공하거나 아래 절차로 특정 실패 버전의 제외가 승인되어야 점검일이 전진합니다. 발표 목록 오류는 계속 차단합니다.
잠금 유실, 파일 저장 실패, API 공통 장애는 전체 실행을 중단합니다. commit 직후 중단된 경우에도 저장된 대상 목록을 통해 재처리합니다.
`checkpoint.json`과 `pending_datasets.json`을 함께 영속 보관하고 임의 수정·삭제하지 마세요. 기존 체크포인트는 그대로 사용할 수 있으며 첫 갱신 시 재시도 파일을 생성합니다.
수집은 같은 주기·기간·품목의 국가를 최대 100개씩 묶으며 검증·적재는 국가별로 유지합니다. 자동 재개 정책은 아래 절차를 따릅니다.

변환 CSV는 확인용으로 저장하며 적재 시 다시 읽지 않습니다. 메모리의 변환 결과에 같은 공통 검증을 적용한 뒤 적재합니다. 비중 계산은 변환·검증이 공유하며 DB의 생성 컬럼과 적재 후 대조합니다.

적재 후 대조는 ORM 객체 대신 필요한 9개 컬럼을 조회합니다. 초기·수동 적재는 입력 복합 키, 월별 교체는 잔여 행 검사까지 포함한 대상 범위를 조회하며, 부모 마스터도 입력에 필요한 키만 확인합니다. 키 목록은 100개씩 나누어 조회합니다.

## 성공한 발표 버전 재처리 방지

`pending_datasets.json`의 `completed_versions`에 국가·주기·기간별 마지막 성공 HS 판본과 `lastReleased` 전체 시각을 저장합니다. 상태 파일의 DB·수집 범위 해시가 일치할 때만 사용합니다. 같은 날짜라도 더 최신 시각이면 새로 처리합니다. 동일 시각의 판본 변경은 충돌로 보류합니다.
성공 표시는 DB commit·전수 검증·범위별 실행 기록 저장 이후에 재시도 목록 제거와 함께 원자적으로 저장합니다. 저장 실패 시 성공했다고 간주하지 않고 다시 처리합니다. 체크포인트만 저장하지 못했다면 성공 버전을 재처리하지 않고 점검일 저장을 재시도합니다.
전체 manifest의 `skipped`는 동일 성공 버전이라 건너뛴 범위 수입니다. 기존 파일에 성공 버전이 없으면 최초 1회는 재처리하여 기록을 생성합니다.
API 발표 목록 조회는 계속 수행합니다. 429 이후 같은 명령을 다시 실행하면 성공 범위를 건너뛰고 미처리 범위를 이어 처리합니다. 호출 예산과 자동 재개를 적용하며, 진행 중인 회차의 발표 조회 종료일은 고정합니다. 완료 후에는 새 발표일 범위를 조회합니다. API가 발표 시각·판본을 바꾸지 않고 내용을 수정하는 경우는 이 버전 비교만으로 감지하지 못합니다. 상태 파일은 DB와 함께 보존하며 외부에서 데이터를 변경한 경우 상태와 DB를 대조해 복구해야 합니다.

## API 공통 장애와 범위별 데이터 오류

API 공통 장애는 `ApiRequestError`로 전달하며 `kind`, `status_code`, `attempts`를 가집니다. 메시지에 특정 문구가 있는지로 분류하지 않습니다.
- 네트워크 오류·HTTP 408·5xx: 요청 하나에서 최대 3회 시도한 뒤에도 실패하면 전체 실행 중단. 다음 국가·기간에서 같은 장애를 반복 시도하지 않습니다.
- HTTP 401/일반 403 및 그 밖의 비정상 HTTP 상태: 즉시 중단. 다른 4xx도 범위 데이터 문제라고 단정할 수 없으므로 보수적으로 중단합니다.
- JSON 파싱 또는 API 공통 응답 구조 오류: 즉시 중단. 원문 응답과 인증 키를 오류 메시지에 넣지 않습니다.
- 정상 응답 안의 국가·기간·금액·판본 등 범위 검증 오류: 해당 범위를 실패로 남기고 다른 범위를 계속 처리합니다. 발표 목록 단계도 범위를 식별할 수 있는 오류는 아래 절차로 분리합니다.

전체 `manifest.json`에 `error_type`, `error`, `api_error_kind`, `http_status`, `api_attempts`, `pending`, `request_count`를 기록합니다. 파일 저장이 가능할 때 기록되며, 미처리 대상과 이전 정상 점검일은 유지합니다. 장애 전 성공한 발표 버전은 복구 후 같은 실행 명령으로 재개할 때 건너뜁니다. 인증·데이터 오류를 제외한 일시적 API 장애는 아래 자동 재개 정책을 따릅니다.

## 발표 목록 오류 보류와 복구

미지원 HS 판본·동일 범위의 원본 판본 충돌·잘못된 발표 시각처럼 국가·주기·기간을 식별할 수 있는 목록 오류는 `pending_datasets.json`의 `catalog_errors`에 저장합니다. 실행 폴더의 `catalog_errors.json`에서도 확인할 수 있습니다. 같은 범위의 정상처럼 보이는 다른 항목이나 기존 재시도 데이터로 우회 적재하지 않습니다. 다른 정상 범위와 충돌하지 않는 기존 재시도 범위는 계속 처리합니다.
오류가 목록에서 사라져도 해제하지 않으며, 정상 발표 항목으로 교정되어야 일반 적재 대기 목록으로 이동합니다. 이후 적재가 실패하면 기존 재시도 목록에 남습니다. 발표 오류 또는 적재 미처리가 하나라도 있으면 정상 점검일을 전진하지 않습니다.
전체 manifest의 `catalog_failed`는 미해결 발표 오류 범위 수, `failed`는 이번 적재 과정에서 실패한 범위 수, `pending`은 적재 대기 수입니다. 발표 오류만 남아 있어도 전체 상태는 `PARTIAL_FAILED`입니다. 기존 성공 버전 건너뛰기는 정상 범위에 계속 적용합니다.
국가·기간을 식별할 수 없는 행, 조회 범위를 벗어난 응답, 목록 조회의 API 공통 장애는 전체 중단을 유지합니다. 같은 판본의 중복 발표는 가장 최근 발표 시각을 사용하며, 서로 다른 원본 판본은 임의로 고르지 않습니다.

CSV 검증은 파일을 연 `with` 블록 안에서 완료합니다. 검증 예외·traceback을 보관하더라도 파일을 닫으며, UTF-8 BOM 지원과 기존 검증 규칙은 유지합니다. 실제 Windows에서의 파일 교체·삭제는 별도 확인이 필요합니다.

## 오래된 발표로의 후퇴 방지

상태 파일의 `known_versions`는 범위별로 확인한 최신 발표 시각·판본을 보존합니다. 성공 여부를 뜻하지 않으며 성공 표시는 `completed_versions`, 미처리 상세는 `datasets`, 오류 보류는 `catalog_errors`로 관리합니다. 기존 상태 파일은 성공·대기 버전에서 최신 기준을 복원합니다.
새 발표가 저장된 최신 기준보다 오래되면 `skipped_stale`를 늘리고 무시합니다. 최신 재시도 대상이 있으면 이를 그대로 처리하며, 기존 발표 오류를 오래된 항목으로 해제하지 않습니다. 같은 시각·같은 판본의 성공은 `skipped`, 같은 시각·다른 판본은 오류 보류, 더 최신 시각은 갱신 대상입니다.
발표 시각은 UTC로 비교합니다. 오프셋 없는 시각은 UTC로 취급하고 `Z`·`+00:00`·다른 오프셋이 같은 순간을 나타내면 동등하게 비교합니다. 외부 API가 발표 시각을 과거로 교정한 경우 자동 반영하지 않으므로 담당자가 원본과 상태를 확인해야 합니다.

## 작업 오류와 오류 기록 저장 실패가 겹치는 경우

범위 검증이 실패한 뒤 실패 manifest·재시도 상태·실패 실행 요약 저장에서도 오류가 발생하면 즉시 실행을 중단합니다. 최초 작업 예외를 최상위로 유지하고 저장 예외를 원인(`__cause__`)으로 연결합니다. 전체 manifest를 저장할 수 있으면 원래 `error_type`·`error`와 별도로 `recording_errors`에 저장 경로·오류 유형·메시지를 기록합니다.
디스크 장애로 모든 기록 파일을 쓸 수 없으면 터미널 로그에서 원래 작업 오류와 저장 오류를 확인해야 합니다. 정상 점검일은 유지하고, 저장 장애 복구 후 같은 상태 경로로 재실행합니다.


## 일시적인 HTTP 429 대응

요청 시작 간격은 기본 2초입니다. 429는 Retry-After(초 또는 HTTP 날짜)에 1초 여유를 더해 같은 요청을 최대 3회 시도합니다. 안내가 없거나 잘못됐으면 3초·5초 대기를 사용합니다. 한 번의 대기가 60초를 넘으면 안내 시간을 줄이지 않고 즉시 중단합니다. 401/일반 403은 즉시 중단합니다. 명시적인 quota 403은 아래 정책을 따릅니다.
응답 파일 옆 `.retry.jsonl`에 시도·대기 시간과 숫자형 제한 정보를 남깁니다. 최종 실패 manifest에는 `api_retry_info`를 기록합니다. 인증 키·응답 원문은 기록하지 않습니다. 이 재시도는 요청 내부에서 수행하며 각 HTTP 시도는 실행당 호출 예산에 포함합니다. 실행 전체의 재개는 아래 정책으로 별도 관리합니다.


UN advisory lock 전용 연결은 잠금을 얻기 전에 연결 풀에서 분리합니다. 따라서 연결 폐기가 취소되더라도 후속 close는 풀 반환 대신 물리 연결 종료를 수행합니다. UN 작업마다 전용 연결을 사용하며 SKN 공통 DB 모듈의 풀 설정은 변경하지 않습니다.


## 묶음 수집·실행 예산·자동 재개

- 묶음 응답에서 국가를 식별할 수 있는 중복·금액 오류는 해당 국가만 실패로 기록합니다. 응답 상한 도달이나 국가 식별 불가는 전체 중단합니다.
- API 재시도 중 호출 예산이 끝나면 마지막 API 오류를 유지하여 2시간·최대 3회 재개 정책을 적용합니다. 장애 없이 예산만 소진했을 때 5분 뒤 재개합니다.
- 기본 HTTP 예산은 실행당 300회입니다. 목록·품목·요청 내부 재시도를 모두 포함하며 캐시 읽기는 제외합니다. 일일 할당량 설정과는 별개입니다.
- 예산 소진은 5분 뒤 재개합니다. 네트워크·명시적 quota 403·HTTP 408/429/5xx 지속 장애는 2시간 뒤 최대 3회 자동 재개합니다(최초 실행과 별도). 서버 Retry-After가 더 길면 그 시간 이상 기다립니다.
- 401/일반 403·기타 비정상 HTTP·응답 구조·데이터 검증·DB/파일 오류는 자동 반복하지 않습니다. 원인을 확인한 후 수동 재실행하세요.
- `continuation.json`에 회차·고정 발표 조회 범위·재개 사유·다음 시각·API 재개 횟수를 저장합니다. `continuations/`에는 요청별 성공 응답과 묶음 계획을 보관합니다. 기존 checkpoint/pending 파일과 함께 영속 보존해야 합니다.
- 스케줄러의 `un_data_resume` 작업이 매분 기한을 확인하므로 실제 재개는 지정 시각 이후 최대 약 1분 지연될 수 있습니다. 대기 중 DB/API 연결·잠금을 보유하지 않습니다. 스케줄러가 꺼져 있으면 자동 실행하지 않으며 재시작 시 저장된 기한을 확인합니다.
- `RETRY_EXHAUSTED`는 자동 재개 3회를 소진한 상태입니다. 담당자가 장애 복구를 확인한 후 `python -m backend.app.scheduler.jobs.un_data_refresh --state-dir <동일 경로> --api-env <설정 파일> --resume-now`로 즉시 재개하고 횟수를 초기화할 수 있습니다.
- DB 반영·검증 완료 범위는 건너뜁니다. 수집 중단 범위는 저장된 성공 요청을 사용하되 해당 국가의 모든 품목이 준비된 뒤 트랜잭션으로 반영합니다. 성공 응답 저장 자체가 실패했으면 그 요청은 다시 호출될 수 있습니다.
- 데이터 오류를 수정해 재실행하는 경우에는 오래된 오류 응답을 재사용하지 않도록 새 회차로 조회합니다. 이미 성공한 발표 버전 표시는 유지합니다. 장시간 중단한 회차를 완료하면 이후 발표분도 5분 뒤 새 회차에서 확인합니다.


## 취소와 비정상 종료 복구

- 실행 전에 `recovery_fence.json`에 새 실행 번호와 `recovery_guard.json` 차단 표식을 영속 저장합니다. 저장 실패 시 수집·적재를 시작하지 않습니다. 상태 확정 후 guard를 삭제하고, 같은 실행 번호의 `recovery_release.json` 완료 기록을 저장해야 해제가 확정됩니다. fence와 release는 삭제하지 않고 다음 실행에서 갱신합니다.
- guard 삭제 전후에 취소되거나 완료 기록 저장이 실패하면 fence와 release의 실행 번호가 불일치하여 자동 재개를 차단합니다. 이전 실행의 완료 기록은 새 실행을 해제할 수 없습니다. 세 파일을 상태 디렉터리와 함께 보존하세요.
- 작업 실패 뒤 정리 중 취소·저장 오류가 발생하면 원래 작업 오류를 유지하고 정리 오류는 로그로 남깁니다.
- Ctrl+C로 전달된 `KeyboardInterrupt`는 `CANCELLED`로 기록합니다. 이 저장이 실패해 기존 `ACTIVE`가 남아도 차단 표식은 유지됩니다. 시작·월별·매분 점검과 일반 수동 실행은 재개하지 않습니다.
- 실행 중인 프로세스가 잠금을 보유하면 `ALREADY_RUNNING`, 잠금은 풀렸지만 차단 표식이 남았으면 `RECOVERY_REQUIRED`로 안내합니다. 차단 상태 확인만으로 표식을 삭제하지 않습니다.
- 디스크 문제와 중단 원인을 확인한 뒤 `python -m backend.app.scheduler.jobs.un_data_refresh --state-dir <동일 경로> --api-env <설정 파일> --resume-now`로 명시적으로 재개합니다. 성공 버전·요청 캐시는 보존합니다. 표식을 수동 삭제하는 방식으로 우회하지 마세요.
- **이전 동작에서 변경:** 강제 종료로 남은 ACTIVE도 차단 표식이 있으면 자동 복구하지 않습니다. 취소 기록 저장 실패와 비정상 종료를 구분할 증거가 없을 때는 사용자 취소 보호를 우선합니다. 표식이 없는 이전 버전 ACTIVE만 실제 잠금 해제를 확인한 뒤 자동 복구합니다.
- SystemExit·SIGTERM·SIGKILL을 사용자 취소로 추정하지 않습니다. 명시적 취소 구분은 Ctrl+C/KeyboardInterrupt입니다. 전체 스케줄러가 종료됐다면 재시작해야 상태를 확인할 수 있습니다.
- 동일 호스트의 OS 파일 잠금과 상태 디렉터리 보존을 전제로 합니다. 파일시스템 자체의 손상이나 상태 파일의 외부 삭제까지 보장하지는 않습니다.


### 완료 확정 시점과 취소의 경계

- 완료 기록은 먼저 별도 준비 파일에 저장하고 fsync·임시 파일 정리를 마칩니다. 그 후 `os.replace(준비 파일, recovery_release.json)`의 원자적 교체가 **실행 종료 결과의 완료 확정 지점**입니다. 성공 경로에는 교체 뒤 파일 정리가 없습니다.
- 확정 전 취소: `CANCELLED`를 기록하고 자동 재개를 차단합니다. 취소 기록 저장까지 실패해도 완료 기록의 실행 번호가 일치하지 않으므로 차단됩니다.
- 확정 후 인터럽트: 해당 실행은 이미 종료 결과가 확정됐습니다. 인터럽트는 호출자에게 전달하지만 그 결과를 `CANCELLED`로 소급 변경하지 않습니다. 따라서 확정된 결과가 `WAITING`이면 기존 기한의 자동 재개 정책이 유지됩니다. 이는 미완료 작업의 취소와 다릅니다.
- 교체 직후 인터럽트로 함수가 반환하지 못한 경우에도, 메모리 플래그가 아니라 디스크 완료 기록의 실행 번호로 확정 여부를 판정합니다. 확인 자체가 불가능하면 상태를 덮어쓰지 않고 오류를 알립니다.
- 이 규칙은 실행 중 취소와 완료 후 중단을 구분합니다. 완료 후 예약된 다음 실행까지 중단하려면 스케줄러를 중지해야 합니다. 반복 SIGINT·디스크 장애·전원 차단 전체를 하나의 원자적 작업으로 처리한다고 보장하지 않습니다.

### 중단·복구 알림과 반복 경고

- 알림은 실행 터미널의 Python 로그로 출력됩니다. 서비스로 실행하면 해당 서비스의 stdout/stderr 로그 수집 설정에서 확인하세요. 이메일·Slack·OS 알림을 발송하는 기능은 없습니다.
- 스케줄러가 최초 차단을 확인하면 `WARNING: UN 갱신 중단 [CANCELLED 또는 RECOVERY_REQUIRED]`와 사유·상태 경로·수동 재개 안내를 출력합니다. CANCELLED 저장 실패는 사용자 취소로 단정하지 않고 미확정 종료로 알립니다.
- 동일한 상태 경로·차단 사유·종료 회차는 다시 경고하지 않습니다. 매분 점검과 자동 재개 차단은 계속 유지하며, 사유나 회차가 바뀌면 새 경고를 출력합니다. 일반 APScheduler 실행 로그나 다른 오류 로그까지 숨기지는 않습니다.
- 중단·복구 알림은 실행과 동일한 `continuation.lock`을 획득한 뒤 최신 파일 상태를 다시 확인합니다. 수동 재개가 실행 중이면 알림을 보류하고, 이미 완료됐다면 과거 CANCELLED 결과로 중단 경고를 내지 않습니다. 알림을 출력할 때까지 잠금을 유지하며 작업의 취소·재개 조건은 변경하지 않습니다.
- 정상적으로 차단이 해제된 것을 확인하면 `INFO: UN 차단 해제 확인`과 현재 상태를 한 번 출력합니다. 이는 데이터 갱신 성공 알림이 아니며, 실행 결과를 별도로 확인해야 합니다.
- 중복 억제 정보는 프로세스 메모리에만 둡니다. 취소 표식·상태 파일은 수정하지 않습니다. 스케줄러를 재시작하면 남아 있는 차단을 한 번 다시 경고합니다.
- 실행 중인 프로세스가 잠금을 보유하면 중단 경고를 내지 않습니다. 스케줄러 자체가 꺼져 있는 동안은 알림을 보낼 수 없습니다. 실행 중에는 매분 점검, 재시작 후에는 시작 점검으로 상태를 확인합니다.
- 재배포·재시작 후 `RECOVERY_REQUIRED` 여부를 확인하세요. 원인과 저장 상태를 점검한 뒤 기존 DB·scope·API 설정 및 동일 상태 경로로 `--resume-now`를 실행합니다. 경고를 없애기 위해 표식을 삭제하거나 초기화하지 마세요.

## 발표일 경계와 2일 중첩 조회

정상 점검일은 기존처럼 KST 실행일로 기록합니다. 발표 목록의 실제 조회 시작일만
정상 점검일보다 2일 앞당깁니다(2022-01-01 이전으로 내려가지 않음).
UTC 발표일과 KST 점검일의 날짜 차이로 빠지는 발표를 다시 확인하기 위한 것입니다.
월별·연간 조회 모두 적용하며 이미 성공한 동일 발표 버전은 다시 적재하지 않습니다.
이 2일은 시간대 경계 대응이며, 장기간 지연 등록된 과거 발표까지 보장하는 전수 재수집은 아닙니다.

## 상태 폴더 영속 보관·백업·복원

Windows에서는 짧은 영속 경로(예: `C:\skn-state\un-data`)를 권장합니다.
승인·취소 감사 세대 전체와 요청을 함께 해시하여 캐시 파일명을 만들며, 긴 세대 폴더는 만들지 않습니다.
기존 세대 폴더의 캐시는 접근 가능한 경우 재사용하고 원본 파일을 보존합니다. Windows 경로 제한으로
구형 캐시에 접근할 수 없다면 해당 응답만 다시 수집해 짧은 경로에 저장합니다. 성공 발표 기록은 유지합니다.
초기화·수동 갱신·자동 재개 전에 가장 긴 캐시 임시 경로까지 계산하여, Windows에서 259 UTF-16 단위를
넘으면 API 호출·적재·상태 변경 전에 중단합니다. 긴 경로 활성화 여부에 의존하지 않는 지원 기준이며
Mac/Linux에는 이 제한을 적용하지 않습니다. 기존 상태가 있다면 아래 전체 백업·복원 절차로 옮기고,
모든 실행 명령의 상태 경로를 함께 변경하세요. 경로 문제를 해결하려고 체크포인트를 삭제하지 마세요.
이 검사는 Mac에서 Windows 경로·오류를 모의하여 검증했으며 실제 Windows 파일시스템 검증은 별도입니다.

배포 코드 경로와 분리한 영속 경로를 최초 적재, 수동 실행, 스케줄러에서 동일하게 사용하세요.
예: `/srv/skn-state/un-data` (팀 서버의 실제 경로와 권한은 담당자 결정).
`--state-dir`와 스케줄러의 `--un-state-dir`에 같은 경로를 지정합니다.
소스 재배포 시 이 폴더를 지우거나 빈 폴더로 바꾸지 마세요.

스케줄러와 수동 실행을 중지한 뒤 아래 명령으로 전체 상태를 백업합니다.
명령은 continuation/refresh 잠금도 확인하므로 실행 중이면 실패합니다.
체크포인트만 복사하면 실패 목록·성공 버전·응답 캐시·취소 표식이 빠질 수 있습니다.

```bash
python -m backend.app.scheduler.jobs.un_data_state backup --source /srv/skn-state/un-data --destination /srv/skn-backup/un-data-20261019
python -m backend.app.scheduler.jobs.un_data_state restore --source /srv/skn-backup/un-data-20261019 --destination /srv/skn-state/un-data-restored
```

백업과 복원 대상은 아직 존재하지 않는 새 폴더여야 합니다. 기존 runtime에 덮어쓰거나 병합하지 않습니다.
파일 목록과 SHA256이 다르면 복원을 중단하고, 심볼릭 링크는 허용하지 않습니다.
복원 명령은 DB 적재나 스케줄러 시작을 수행하지 않습니다. 복사 완료 메시지 후에만 새 경로를 사용하세요.
취소·복구 차단 상태도 그대로 보존합니다. `CANCELLED`/`RECOVERY_REQUIRED`를 확인한 담당자만
`--resume-now`로 수동 재개합니다. 자동 재개를 위해 표식을 삭제하지 마세요.

백업 시점 뒤에 DB가 갱신됐다면 먼저 DB와 백업 상태를 대조해야 합니다.
옛 상태와 최신 DB를 무조건 조합하면 이미 반영된 범위를 재처리할 수 있습니다.
배포 전과 정상 실행 후 백업을 권장하며, DB 백업과 상태 백업의 대응 시점도 기록하세요.
백업 없는 상태 전체 유실은 자동 복구할 수 없습니다. 임의 점검일 생성이나 초기 CSV 재적재로
우회하지 말고 DB 백업·실행 이력으로 복구 범위를 담당자가 확정해야 합니다.

## MySQL DB 식별과 접속 주소 변경

MySQL에서는 `SELECT @@server_uuid, DATABASE()`로 실제 서버와 DB 이름을 확인합니다.
체크포인트에 `database_identity`가 연결된 뒤에는 같은 서버·DB의 호스트 별칭이나 계정 변경을
다른 DB로 오인하지 않습니다. 다른 서버 UUID/DB 이름 또는 식별 조회 실패는 중단합니다.
체크포인트의 기존 `target_sha256`은 pending·continuation 연결 키로 유지합니다.

구형 체크포인트는 **원래 접속 설정으로 1회 정상 실행하여 식별자를 연결한 뒤** 주소를 변경하세요.
구형 파일에 서버 UUID가 없으므로 다른 주소가 같은 DB인지 자동 추측하지 않습니다.
식별자 연결은 기존 URL 일치 확인 및 실제 DB 조회 후, refresh/DB 잠금 하에서 저장합니다.
DB 복제·서버 교체·백업 복원으로 UUID가 달라지면 운영자가 데이터와 상태를 검증해야 합니다.
JSON의 UUID/해시를 임의로 수정하는 방법은 지원하지 않습니다.

## HS2022 전용 정책 (2026-10-19 적용)

### 데이터·DB 인계 기준: 0, NULL, 제외 범위

UN 적재는 누락을 0으로 채우지 않습니다. CSV 금액의 빈 칸은 DB `NULL`, 실제 관측 금액 0은
숫자 0으로 유지합니다. 한국 금액 또는 세계 금액이 없거나 세계 금액이 0이면 한국 비중은
`NULL`입니다. 세계 금액이 양수이고 한국 금액이 실제 0이면 비중은 0입니다.
비중은 반올림된 계산값이므로 비중 0만으로 한국 금액도 0이라고 판단하지 마세요.
원천 행 자체가 없으면 가상의 0행을 만들지 않습니다. M/A는 별도 통계 주기이므로
연간 값과 월별 값을 혼용하거나 없는 월을 연간 값으로 채우지 않습니다.

현재 67,550행에는 세계 금액 NULL 1행, 한국 금액 NULL 17,124행, 비중 NULL 17,125행이 있습니다.
금액의 실제 0행은 없지만 코드·회귀 테스트에서는 0을 별도로 검증합니다. 비중 0인 1행은
양수 금액의 반올림 결과입니다. 최초 CSV만으로 NULL의 구체적인 원인을 역추정하지 않습니다.

인계 파일(둘 다 DB 적재 대상 아님):

- `data/un_data/hs2022_exclusions.csv`: 최초 스냅샷에서 제외된 **8,641행**의 실제 키 목록.
  `freq_code`, `period_start`, `country_code`(ISO2), `hs6_code`(6자리 문자열),
  `source_hs_ver`, `reason`을 제공합니다. `reason=HS2022_ONLY`는 구판 관측 자료의 정책 제외입니다.
- `data/un_data/hs2022_exclusions_summary.json`: 원본 Git 커밋·원본/최종/제외 파일 SHA256,
  전체 제외 16개국·일부 제외 45개국, 판본·연도별 제외 행 수와 NULL/0 집계입니다.
  초기 2026-10-15 스냅샷에 대한 기록이며, 이후 API 전체를 다시 확인했다는 의미가 아닙니다.

월별 실행은 `runs/<실행>/excluded_hs_policy.json`에 국가 코드·주기·기간·기존 HS 판본·
`target_hs6_codes`·사유·발표 시각을 기록합니다. `target_hs6_codes`는 설정된 수집 대상 품목이며
`evidence_level=DATASET_ANNOUNCEMENT_ONLY`이므로 그 품목의 RAW 존재 여부는 확인하지 않았습니다.
초기 제외 CSV의 실제 관측 키와 이 월별 대상 범위를 같은 근거로 취급하지 마세요.

후속 API/화면 담당자는 국가·품목·주기·기간 단위로 다음을 구분해야 합니다.

| 근거 | 의미 및 인계 기준 |
|---|---|
| 현재 `un_data`의 금액 0 | 실제 관측값 0. 미제공으로 바꾸지 않음 |
| 현재 `un_data`의 금액 NULL | 금액 확인 불가. 0으로 변환하지 않음 |
| `missing_amounts.json`의 `KOREA_ROW_MISSING` | 한국 행 없음. 해당 실행의 원천 검증 근거 |
| `missing_amounts.json`의 `KOREA_SAME_BASIS_AMOUNT_MISSING` | 한국 행은 있으나 세계 금액과 같은 CIF/FOB 금액 없음. 다른 기준으로 대체하지 않음 |
| 초기 제외 CSV의 정확한 키 + 현재 HS2022 행 없음 | 초기 자료는 구판 정책으로 제외됨. UN의 영구 미제공을 뜻하지 않음 |
| 조회 결과 없음이나 실행 실패만 확인됨 | 사유 미확인/갱신 상태를 추가 확인. 자동으로 정책 제외 또는 실제 0으로 분류하지 않음 |

초기 제외 목록은 과거 이력입니다. 이후 동일 키의 HS2022 행이 적재됐다면 현재 값을 우선합니다.
갱신 실패나 승인 제외가 있어도 이전 정상 행을 보존할 수 있으므로 존재하는 값을 미제공으로
덮어 표시하지 마세요. 비교 자료가 없으면 증감률을 계산하지 않고, 전년 값이 실제 0인 경우도
분모 0으로 산출 불가임을 구분합니다. 이 문서는 데이터 의미의 인계 기준이며 화면/API 구현은 포함하지 않습니다.

초기 CSV는 기존 76,191행에서 HS2022 67,550행만 선택한 파생 스냅샷입니다.
필요 부모 목록은 137개 국가·15개 HS2022 품목입니다. 8,641행은 구판 정책 제외이며
금액·국가·통계 기간·HS 코드를 HS2022로 변환하거나 값을 다시 계산하지 않았습니다.
최초 정상 점검일은 원본 수집 증거의 2026-10-15를 그대로 사용합니다. 10월 19일은
필터링 작업일이며 새로운 API 정상 점검일이 아닙니다. SNAPSHOT에 원본 CSV 해시를 보존합니다.

수집 대상 153개 국가·15개 품목과 기존 M/A 구분은 유지합니다. 지금 HS2022 데이터가 없는
국가도 추후 H6 원보고 자료가 발표되면 수집할 수 있습니다. 실제 응답에 필요한 부모 마스터가
없으면 기존처럼 해당 범위가 실패하며 담당자 보완 후 재개합니다.
발표 목록의 알려진 구판(H0~H5)은 정책 제외로 기록하고 수집하지 않습니다.
실행 폴더 excluded_hs_policy.json과 manifest의 excluded_hs_policy 건수로 확인합니다.
이는 성공 버전 재처리 방지 skipped와 다른 지표입니다. 미지원 판본·모순되는 동일 시각 판본은
여전히 오류로 보류합니다. RAW 변환·CSV 검증·적재 입력은 HS2022만 허용합니다.
정책 제외는 기존 HS2022 실적의 자동 삭제 지시가 아니며 구판 금액으로 덮어쓰지 않습니다.

기존 다중 판본 scope와 상태 파일은 새 scope 해시가 달라 자동 재사용하지 않습니다.
새 설치는 빈 UN 테이블과 새 상태 경로에서 --initialize-csv를 사용하세요.
이미 다중 판본 데이터를 적재했다면 임의로 scope 해시를 수정하거나 기존 체크포인트를 삭제해
초기화를 강행하지 마세요. 백업 후 담당자가 DB·상태 전환 계획을 별도로 확정해야 합니다.
이번 작업은 운영 DB에서 구판 행을 삭제하거나 기존 상태를 강제 마이그레이션하지 않습니다.


## P3: 담당자 승인에 따른 특정 실패 발표 제외

자동 실패 횟수 기준 제외는 없습니다. 먼저 `list`로 실패 범위, 발표 시각, 오류를 확인합니다.
실제 담당자의 승인을 받은 운영자가 담당자 이름과 구체적인 사유를 입력합니다. 이름 입력 자체가
신원 인증은 아니므로 상태 디렉터리 쓰기 권한은 승인 권한이 있는 운영자로 제한해야 합니다.

```sh
python -m backend.app.scheduler.jobs.un_data_exclusions list --state-dir data/un_data/runtime
python -m backend.app.scheduler.jobs.un_data_exclusions approve --state-dir data/un_data/runtime --scope-key A_2023_40 --release 2024-02-01 --approver "담당자 이름" --reason "검토한 원천 오류와 제외 사유"
python -m backend.app.scheduler.jobs.un_data_exclusions revoke --state-dir data/un_data/runtime --scope-key A_2023_40 --release 2024-02-01 --approver "담당자 이름" --reason "원천 수정 확인 및 재처리 요청"
```

위 범위/시각은 예시이며 `list`의 실제 값을 정확히 사용합니다. `FAILED` 데이터셋만 승인할 수 있고,
발표 버전을 특정할 수 없는 `catalog_errors`는 승인 제외할 수 없습니다.
승인·취소는 continuation → refresh 순서로 잠그고, 승인 상태와 감사 이력을 같은
`pending_datasets.json`에 원자적으로 기록합니다. 성공 버전으로 표시하거나 기존 DB 행을 삭제하지 않습니다.
실행별 `excluded_approved.json`과 `manifest.excluded_approved`로 실제 제외 적용을 확인합니다.
새 발표에는 과거 승인이 적용되지 않습니다. 이전 승인 취소 후 새 실패를 다시 검토·승인해야 합니다.
취소는 새 버전/성공 버전을 덮지 않으며, 목록 조회 기간에서 벗어난 기존 승인 버전도 재시도 큐에 복원합니다.
감사 이력이 바뀌면 요청 캐시 세대를 바꾸므로 승인 취소 후 오래된 실패 RAW를 재사용하지 않습니다.
기존 감사 이력·캐시는 보존합니다. 승인 자체는 실행이나 점검일 전진을 수행하지 않습니다.
기존 취소/불확실 종료 차단 표식도 유지하므로, 해당 상태는 확인 후 `--resume-now`로만 재개합니다.

## P3: quota 403의 보수적 분류

[UN 공식 API 설명](https://uncomtrade.org/docs/un-comtrade-api/)은 Azure API Management 사용을 명시하고,
[Microsoft quota 문서](https://learn.microsoft.com/en-us/azure/api-management/quota-policy)는 quota 소진 시
403과 Retry-After를 설명합니다. 모든 403이 quota라는 뜻은 아닙니다.
구현은 JSON `statusCode=403`, 명시적인 APIM `Out of call volume quota. Quota will be replenished in ...`
메시지 형식, 유효한 Retry-After가 모두 있을 때만 `kind=quota`로 분류합니다.
인증/권한 오류, 모호한 메시지, 헤더만 있는 403은 자동 재시도하지 않습니다.
quota는 429와 같은 요청당 최대 3회/대기 60초 제한 및 회차당 최대 3회 재개를 적용합니다.
31일보다 긴 재개 대기는 시간을 단축하지 않고 자동 재개를 종료해 운영자 확인을 요구합니다.
분류 검증은 모의 응답으로 수행했으며 실제 quota를 소진시키는 호출은 하지 않았습니다.
